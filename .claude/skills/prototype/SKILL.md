# Prototype — สร้าง/อัปเดต UI mockup จาก Requirement + Backlog + Feature List + User Journey

Skill นี้ทำงานใน main conversation ทั้งหมด (กำหนดขอบเขต, ตรวจสอบ Design System, ตัดสินใจเรื่อง version, และเสนอแผนให้ user ยืนยัน) แล้วค่อยส่งงานเขียนไฟล์ให้ subagent `prototype-writer` ทำในขั้นตอนสุดท้ายเท่านั้น **ห้ามข้ามขั้นตอนเสนอแผน (ขั้นตอน 5) ไปเรียก subagent ตรง ๆ ไม่ว่ากรณีใด**

## ขั้นตอน

### 1. สำรวจข้อมูลต้นทาง

- Read `docs/01-requirements/backlog.md` และ `docs/01-requirements/feature-list.md` (ถ้ามี)
- Glob `docs/01-requirements/01-spec/*.md` (ยกเว้น `index.md`)
- Glob `docs/02-design/01-prototypes/*-journey.md` เพื่อดูว่า requirement ไหนมี user journey แล้วบ้าง
- Glob `docs/02-design/01-prototypes/mockups/*/index.md` เพื่อดูว่ามี prototype version อยู่แล้วกี่เวอร์ชัน และครอบคลุม requirement ไหนไปแล้วบ้าง

### 2. กำหนดขอบเขต (scope) — ถามเมื่อ user ไม่ได้ระบุเจาะจงมา

- ถ้า user ระบุ requirement/feature/ฟีเจอร์เจาะจงมาแล้วในคำขอ (เช่น ชื่อ feature จาก feature-list.md หรือ path spec ตรง ๆ) ใช้ตามนั้นได้เลย ไม่ต้องถามซ้ำ
- ถ้า user ไม่ได้ระบุ ให้ AskUserQuestion พร้อมตัวเลือกอย่างน้อย 3 แบบ พร้อมข้อดี/ข้อเสีย เช่น:
  1. **ทำให้ครบทุก requirement ใน backlog** — ข้อดี: ได้ prototype ภาพรวมทั้งระบบในรอบเดียว เห็นความสอดคล้องข้ามหน้าจอ; ข้อเสีย: ใช้เวลา/ไฟล์เยอะ ถ้ามี requirement จำนวนมากอาจไม่จำเป็นต้องทำทั้งหมดตอนนี้
  2. **เลือกเฉพาะ requirement/feature บางรายการ** (ให้ user เลือกจาก list) — ข้อดี: โฟกัสเฉพาะส่วนที่ต้องการรีวิวตอนนี้ เร็วกว่า; ข้อเสีย: อาจเห็นภาพรวมไม่ครบ ต้องกลับมาทำเพิ่มทีหลัง
  3. **ทำเฉพาะ requirement ที่ยังไม่มี prototype เลย** (ส่วนที่มีอยู่แล้วข้ามไป) — ข้อดี: ไม่ทำงานซ้ำ ประหยัดเวลา; ข้อเสีย: ถ้า requirement เดิมมีการเปลี่ยน spec ไปแล้ว prototype เก่าจะไม่ถูกอัปเดตตามในรอบนี้
- ถ้า requirement ที่เลือกยังไม่มี user journey ให้แจ้ง user ว่าจะใช้ spec เป็นฐานกำหนดหน้าจอแทน (แม่นยำน้อยกว่ามี journey) และเสนอทางเลือกว่าจะรัน skill `user-journey` ให้ก่อนหรือไม่

### 3. ตรวจสอบ Design System (`DESIGN.md`)

Glob `docs/02-design/01-prototypes/DESIGN.md`

- **ถ้ามีอยู่แล้ว** → Read เพื่อสรุป design token หลัก (สี, font, spacing, component pattern) ไว้ใช้อ้างอิงตอนเสนอแผนในขั้นตอน 5 ข้ามไปขั้นตอน 4
- **ถ้ายังไม่มี** → ต้องถาม user ก่อนเสมอด้วย AskUserQuestion อย่างน้อย 3 แนวทาง เพื่อรวบรวมข้อมูลไปสร้าง `DESIGN.md`:
  1. **เลือกจากธีมสำเร็จรูป** (เช่น Warm & Earthy, Modern Minimal, Playful Pastel) แล้วให้ Claude ขยายเป็น design token เต็มรูปแบบ — ข้อดี: เร็ว ตัดสินใจง่าย; ข้อเสีย: อาจไม่ตรงกับภาพลักษณ์แบรนด์จริงทั้งหมด ต้องปรับทีหลัง
  2. **อธิบายโทนสี/สไตล์ที่ต้องการเป็นคำพูดเอง** (เช่น สีหลัก, ความรู้สึกที่อยากให้แบรนด์สื่อถึง) — ข้อดี: ตรงกับที่ user คิดไว้มากที่สุด; ข้อเสีย: ต้องใช้เวลาอธิบายและอาจต้องถามต่อเพื่อความชัดเจน
  3. **ส่งภาพตัวอย่าง/โลโก้มาให้วิเคราะห์** — ข้อดี: ได้สีและสไตล์ที่แม่นยำใกล้เคียงของจริง; ข้อเสีย: ต้องมีภาพอยู่แล้ว และ Claude ต้องตีความจากภาพซึ่งอาจต้องยืนยันสีที่แกะออกมาอีกรอบ
  - ถ้ายังตอบไม่ครบ (เช่น เลือกธีมสำเร็จรูปแต่ไม่ได้บอกโทนเสียง/แนวภาพ) ให้ถามต่อจนได้ข้อมูลพอจะสร้าง `DESIGN.md` ตามโครง: Brand Identity & CI, Design Tokens (Colors/Typography/Spacing/Border Radius/Elevation), UI Components & Patterns, UX Guidelines & Rules
  - เก็บคำตอบทั้งหมดไว้ส่งต่อให้ subagent ในขั้นตอน 6 (ให้ subagent เป็นคนเขียนไฟล์จริง ไม่เขียนเองใน main conversation)

### 4. ตรวจสอบ prototype version ที่มีอยู่ — ถามทุกครั้งที่มีของเดิมทับซ้อนกับขอบเขต

จากผลของขั้นตอน 1 (Glob `mockups/*/index.md`):

- **ถ้ายังไม่เคยมี prototype มาก่อนเลย** → ข้ามคำถามนี้ ใช้ `v1` เป็น version ใหม่ทันที
- **ถ้ามี prototype เดิมอยู่แล้ว และ requirement ในขอบเขตรอบนี้ทับซ้อนกับของเดิม (บางส่วนหรือทั้งหมด)** → ต้องถาม user ทุกครั้ง (ไม่ว่าจะเคยถามในรอบก่อนหน้าแล้วหรือไม่) ด้วย AskUserQuestion พร้อมคำแนะนำกำกับแต่ละตัวเลือก:
  1. **สร้าง Folder Version ใหม่ (v{N+1})** — แนะนำเมื่อ: มีการเปลี่ยนแปลง requirement/design แบบมีนัยสำคัญ, ต้องการเก็บ prototype เก่าไว้เทียบ/ย้อนดูประวัติการตัดสินใจ, หรือกำลังจะนำ version เดิมไปใช้ทดสอบกับ user จริงอยู่ (ไม่อยากให้เปลี่ยนกลางคัน)
  2. **แก้ไข Folder เดิม (v{N})** — แนะนำเมื่อ: เป็นการปรับแก้เล็กน้อย (เช่น แก้สี, ข้อความ, ลำดับ element) ที่ยังไม่ finalize, หรือ version เดิมยังไม่เคยถูกใช้รีวิว/ทดสอบจริงเลย ไม่จำเป็นต้องเก็บประวัติแยก
  - ถ้า user ยังตัดสินใจไม่ได้ ให้แนะนำ default เป็น "แก้ไข Folder เดิม" เมื่อการเปลี่ยนแปลงจำกัดอยู่ที่ไม่กี่หน้าจอ/ไม่กระทบ design token หลัก และแนะนำ "สร้าง Folder Version ใหม่" เมื่อขอบเขตรอบนี้ครอบคลุม requirement ใหม่จำนวนมากหรือ DESIGN.md เพิ่งถูกแก้ไขแบบมีนัยสำคัญ
- ถ้ามี prototype เดิมแต่ไม่ทับซ้อนกับขอบเขตรอบนี้เลย (เป็น requirement คนละชุด) → ไม่ต้องถาม ใช้ path ของ version ล่าสุดต่อ (append หน้าจอใหม่เข้า version เดิม) เว้นแต่ user จะระบุอยากแยก version เอง

### 5. เสนอแผนให้ user ยืนยันก่อนเสมอ

สรุปแผนทั้งหมดเป็นข้อความให้ user อ่านก่อนเรียก subagent (ห้ามข้ามขั้นตอนนี้แม้กรณีดูชัดเจนแล้วก็ตาม):

- requirement/feature ที่จะทำ prototype ในรอบนี้ (รายชื่อ + running number)
- จำนวน/รายชื่อหน้าจอโดยประมาณต่อ requirement (อ้างอิงจาก journey หรือ spec)
- Design system ที่จะอ้างอิง (มีอยู่แล้ว หรือจะสร้างใหม่พร้อมสรุปโทน/สีที่เลือกจากขั้นตอน 3)
- Version folder ที่จะใช้ (ใหม่ v{N+1} หรือแก้ไข v{N}) พร้อมเหตุผล

ใช้ AskUserQuestion ถามยืนยัน (ตัวเลือกอย่างน้อย 3 แบบ) เช่น "ยืนยันทำตามแผนนี้เลย" / "ขอปรับขอบเขต (ตัดบางหน้าจอ/เพิ่ม requirement)" / "ขอยกเลิกก่อน ยังไม่พร้อมตอนนี้" ถ้า user เลือกปรับแผน ให้กลับไปทำขั้นตอนที่เกี่ยวข้องซ้ำจนกว่าแผนจะถูกยืนยัน

### 6. ส่งงานให้ subagent `prototype-writer`

เรียก Agent tool ด้วย `subagent_type: "prototype-writer"` (foreground เพื่อรอผลก่อนตอบ user) พร้อมส่ง:

- วันที่ปัจจุบัน (YYYY-MM-DD)
- รายการ `{spec path, journey path}` ทั้งหมดตามแผนที่ยืนยันแล้ว
- ขอบเขตหน้าจอ/บทบาทที่ตกลงกันในขั้นตอน 5 (ถ้ามีการปรับจาก default)
- การตัดสินใจ version: โหมด `new` พร้อมเลข version ถัดไป หรือโหมด `edit` พร้อม path โฟลเดอร์ล่าสุด
- (ถ้ามี) คำตอบทั้งหมดของ user จากขั้นตอน 3 สำหรับสร้าง `DESIGN.md` ใหม่

### 7. รายงานผลกลับ user

สรุป path โฟลเดอร์ version, รายชื่อไฟล์ .html ที่สร้าง/แก้ไข, และแจ้งว่า `DESIGN.md` ถูกสร้างใหม่ในรอบนี้หรือไม่ ถ้าเป็นไปได้ให้แนะนำ user เปิดไฟล์ผ่าน browser เพื่อรีวิว mockup จริง

## หมายเหตุ

- ห้ามลบโฟลเดอร์ version เดิมหรือไฟล์ prototype เดิมเด็ดขาด ถ้าต้องเลิกใช้ version ใดให้เสนอย้ายไป `docs/00-archived/` แทน (อย่าย้ายเองโดยไม่ถาม)
- Path มาตรฐานของ mockup: `docs/02-design/01-prototypes/mockups/v{N}/{RUNNING_NO}-{screen-slug}.html`
- ทุกครั้งที่มีการเรียก skill นี้ซ้ำ (requirement ใหม่ / ขอปรับ prototype เดิม) ต้องทำขั้นตอน 4 (ถามเรื่อง version ใหม่ vs แก้ไขเดิม) และขั้นตอน 5 (เสนอแผนยืนยัน) ใหม่ทุกรอบ ห้ามข้ามโดยอ้างว่าเคยถามไปแล้วในรอบก่อนหน้า
