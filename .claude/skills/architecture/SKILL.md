# Architecture — สร้าง/อัปเดต High-Level Architecture เชิงแนวคิด

Skill นี้ทำงานใน main conversation ทั้งหมด (สำรวจแหล่งข้อมูล, กำหนดกรอบแนวคิดสถาปัตยกรรม, เคลียร์ประเด็นคลุมเครือ) แล้วค่อยส่งงานเขียนไฟล์ให้ subagent `architecture-writer` ทำในขั้นตอนสุดท้ายเท่านั้น ไฟล์นี้เป็น **living document เดียวต่อโปรเจกต์** เหมือน `test-plan` ไม่มีขั้นตอนกำหนดขอบเขตเฉพาะบางรายการเหมือน acceptance-criteria/test-case เพราะสถาปัตยกรรมระดับ high-level ต้องมองภาพรวมทั้งระบบเสมอ

**กติกาที่ต้องคุมตลอด skill นี้:** เอกสารผลลัพธ์ต้องเป็นสถาปัตยกรรมเชิงแนวคิด (conceptual) เท่านั้น ห้ามมีชื่อเทคโนโลยี เฟรมเวิร์ก ไลบรารี หรือฐานข้อมูลใด ๆ ปรากฏในเนื้อหา ถ้า user พยายามระบุ tech stack มาระหว่างทาง ให้แจ้งว่าเอกสารนี้จงใจไม่ผูกกับ tech stack และเสนอให้เก็บรายละเอียดนั้นไว้ทำเป็นเอกสารแยกใน `02-technical/` ภายหลังแทน

## ขั้นตอน

### 1. สำรวจข้อมูลต้นทาง

- Read `docs/01-requirements/backlog.md` และ `docs/01-requirements/feature-list.md` (ถ้ามี)
- Glob `docs/01-requirements/01-spec/*.md` (ยกเว้น `index.md`)
- Glob `docs/02-design/01-prototypes/*-journey.md` เพื่อดูว่า backlog item ไหนมี journey แล้วบ้าง
- Glob `docs/02-design/02-technical/high-level-architecture.md` เพื่อดูว่ามีไฟล์เดิมอยู่แล้วหรือไม่ (Read ถ้ามี เพื่อดูกรอบแนวคิด/ประเด็นคลุมเครือที่เคยตัดสินใจไว้แล้ว)
- Glob `docs/02-design/02-technical/tech-stack.md` — ถ้ามี ให้ Read เพื่อเตรียมส่งต่อ subagent สำหรับเขียนหัวข้อ "Technical Mapping" ท้ายไฟล์ (ไม่ต้องถาม user อะไรเพิ่มสำหรับส่วนนี้ เพราะเป็นการอ้างอิงการตัดสินใจที่มีอยู่แล้ว ไม่ใช่ประเด็นคลุมเครือใหม่)

### 2. แจ้ง user ถ้ามี backlog item ที่ยังไม่มี journey

ถ้ามี backlog item (โดยเฉพาะที่เป็น Must/Should have ใน feature-list) ที่ยังไม่มีไฟล์ journey ให้แจ้ง user ว่ารายการเหล่านั้นจะใช้ spec เป็นฐานสร้าง data flow แทน (แม่นยำน้อยกว่ามี journey) และเสนอทางเลือกว่าจะรัน skill `user-journey` ให้ก่อนหรือไม่ (ไม่บังคับ — ถ้า user อยากทำต่อเลยก็ทำได้)

### 3. กำหนดกรอบแนวคิดสถาปัตยกรรม (architecture framing) — ถามเสมอถ้ายังไม่เคยตัดสินใจไว้

ถ้าไฟล์เดิมยังไม่มี หรือยังไม่เคยระบุกรอบแนวคิดไว้ชัดเจน ให้ AskUserQuestion พร้อมตัวเลือกอย่างน้อย 3 แบบ พร้อมข้อดี/ข้อเสีย เช่น:

1. **แบ่งเป็น layer แบบง่าย** (เช่น ส่วนที่ผู้ใช้โต้ตอบ / ส่วนประมวลผลหลัก / ส่วนเก็บข้อมูล / ระบบภายนอก) — ข้อดี: เข้าใจง่าย สื่อสารกับ non-technical stakeholder ได้ทันที เหมาะกับทีมเล็ก; ข้อเสีย: รายละเอียดน้อย อาจไม่พอให้ทีมพัฒนาแตกงานต่อโดยตรง
2. **C4-style conceptual (Context + Container ระดับแนวคิด)** — ข้อดี: เป็นมาตรฐานสากล เห็น boundary ของระบบและการเชื่อมต่อกับภายนอกชัดเจน ต่อยอดไปสู่การออกแบบเทคนิคละเอียดได้ง่าย; ข้อเสีย: ต้องใช้เวลาทำความเข้าใจ concept ถ้าทีมไม่คุ้นเคยกับ C4 model มาก่อน
3. **แบ่งตาม business capability / domain** (เช่น "การสั่งอาหาร", "การชำระเงิน", "การจัดการสต็อก") — ข้อดี: สอดคล้องกับภาษาธุรกิจ เห็นขอบเขตความรับผิดชอบของแต่ละส่วนชัด รองรับการแตกเป็นทีม/บริการย่อยในอนาคต; ข้อเสีย: ถ้าระบบยังเล็กและมีทีมเดียว อาจดู over-engineered เกินความจำเป็นตอนนี้

ถ้า user เลือกไม่ถูก ให้แนะนำ default เป็นตัวเลือก 1 (layer แบบง่าย) เมื่อ feature-list ยังมีขนาดเล็ก/ทีมเดียว และแนะนำตัวเลือก 3 เมื่อ feature-list เริ่มมีหลาย business capability ที่แยกจากกันชัดเจน

### 4. เคลียร์ประเด็นสถาปัตยกรรมเชิงแนวคิดอื่นที่ spec ยังไม่ระบุชัดเจน — ถามเมื่อจำเป็น

ตรวจสอบ backlog/spec/journey ว่ามีประเด็นที่กระทบโครงสร้างสถาปัตยกรรมระดับแนวคิดแต่ยังไม่ถูกระบุไว้หรือไม่ เช่น:

- ต้องการให้ข้อมูลระหว่างบทบาท (เช่น ลูกค้า-บาริสต้า-พนักงานเสิร์ฟ) ซิงก์กันแบบทันที (real-time) หรือรีเฟรช/แจ้งเตือนเป็นระยะก็เพียงพอ
- ระบบต้องรองรับหลายสาขา/หลายจุดขายพร้อมกันหรือไม่ หรือโฟกัสสาขาเดียวก่อน
- ต้องรองรับการทำงานต่อเนื่องเมื่อเครือข่ายขัดข้อง (offline-first) หรือยอมรับว่าต้องมีอินเทอร์เน็ตตลอดเวลา

ถ้าประเด็นไหนกระทบโครงสร้าง diagram อย่างมีนัยสำคัญและยังไม่ชัดเจน ให้ AskUserQuestion ถามพร้อมตัวเลือกอย่างน้อย 3 แบบต่อประเด็น (พร้อมข้อดี/ข้อเสีย) เช่น สำหรับเรื่อง real-time:

1. **ไม่ระบุตอนนี้** (ปล่อยเป็น open question ในเอกสาร) — ข้อดี: ไม่ต้องตัดสินใจก่อนมีข้อมูลพอ; ข้อเสีย: diagram data flow จะไม่สามารถระบุลักษณะการไหลของข้อมูล (ทันที vs เป็นระยะ) ได้ชัดเจน
2. **ระบุว่าต้องการแบบทันที (real-time)** — ข้อดี: ออกแบบ data flow ให้รองรับการอัปเดตสถานะทันทีตั้งแต่ต้น ลด rework ภายหลัง; ข้อเสีย: อาจเพิ่มความซับซ้อนของสถาปัตยกรรมเชิงแนวคิดโดยไม่จำเป็นถ้าจริง ๆ แล้วไม่ critical
3. **ระบุว่ารีเฟรช/แจ้งเตือนเป็นระยะก็พอ** — ข้อดี: สถาปัตยกรรมเรียบง่ายกว่า; ข้อเสีย: ถ้าภายหลังพบว่าต้อง real-time จริง จะต้องออกแบบ data flow ใหม่บางส่วน

ถ้าไม่มีประเด็นแบบนี้ที่กระทบอย่างมีนัยสำคัญ ให้ข้ามขั้นตอนนี้ไปได้เลย

### 5. ส่งงานให้ subagent `architecture-writer`

เรียก Agent tool ด้วย `subagent_type: "architecture-writer"` (foreground เพื่อรอผลก่อนตอบ user) พร้อมส่ง:

- วันที่ปัจจุบัน (YYYY-MM-DD)
- กรอบแนวคิดสถาปัตยกรรมที่ตกลงในขั้นตอน 3
- ขอบเขต journey/spec ทั้งหมดที่ต้องครอบคลุม (ปกติคือทุกรายการที่มีอยู่ในปัจจุบัน) พร้อมระบุรายการที่ไม่มี journey อ้างอิง (ถ้ามี)
- คำตอบทั้งหมดจากขั้นตอน 4 (ถ้ามี) หรือระบุว่า "ไม่มีประเด็นเพิ่มเติมนอกจาก spec ที่มีอยู่"
- หมายเหตุว่ามี/ไม่มี `docs/02-design/02-technical/tech-stack.md` ให้อ้างอิง ถ้ามีให้ส่งสรุป stack ต่อ layer จากขั้นตอน 1 ไปด้วย (สำหรับเขียนหัวข้อ "Technical Mapping" ท้ายไฟล์)

### 6. รายงานผลกลับ user

สรุป path ไฟล์ high-level-architecture.md, journey/requirement ที่ครอบคลุมในรอบนี้, และประเด็นที่ยังค้างเป็น open question (ถ้ามี) พร้อมชวน user เพิ่มข้อมูลได้ภายหลังด้วยการรัน `/architecture` ซ้ำเมื่อมี requirement/journey ใหม่

## หมายเหตุ

- ไฟล์ `docs/02-design/02-technical/high-level-architecture.md` เป็น living document เดียวของทั้งโปรเจกต์ — อัปเดตทับเนื้อหาหลักเสมอ แต่คงหัวข้อ "ประวัติการแก้ไข" ท้ายไฟล์ไว้ (ต่อท้าย ไม่ลบของเดิม)
- เอกสารนี้เป็นชั้นแนวคิดที่มาก่อนเอกสารเทคนิคเฉพาะอื่นในโฟลเดอร์เดียวกัน (database schema, API design, การเลือกเทคโนโลยี) — เมื่อทีมเลือก tech stack แล้ว ให้เก็บรายละเอียดเชิงเทคนิคเต็มรูปแบบไว้ใน `tech-stack.md` เท่านั้น ไฟล์นี้เพิ่มได้แค่หัวข้อ "Technical Mapping" สรุป mapping ท้ายไฟล์ (ตามที่ระบุในขั้นตอน 5) ห้ามนำรายละเอียด tech stack อื่นมาผสมในหัวข้อ 1-9
