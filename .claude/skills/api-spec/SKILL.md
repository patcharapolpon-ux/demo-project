# API Spec — สร้าง/อัปเดต API Spec เชิงแนวคิด

Skill นี้ทำงานใน main conversation ทั้งหมด (สำรวจแหล่งข้อมูล, กำหนดกรอบการจัดกลุ่ม operation, เคลียร์ประเด็นคลุมเครือ) แล้วค่อยส่งงานเขียนไฟล์ให้ subagent `api-spec-writer` ทำในขั้นตอนสุดท้ายเท่านั้น ไฟล์นี้เป็น **living document เดียวต่อโปรเจกต์** เหมือน `architecture`/`database-schema` ไม่มีขั้นตอนกำหนดขอบเขตเฉพาะบางรายการเหมือน acceptance-criteria/test-case เพราะ operation หลายตัวใช้เอนทิตี/องค์ประกอบร่วมกันข้าม feature

**กติกาที่ต้องคุมตลอด skill นี้:** เอกสารผลลัพธ์ต้องเป็นสัญญาการทำงานเชิงแนวคิด (conceptual) เท่านั้น ห้ามมี HTTP method, URL path, status code, ชื่อ protocol (REST/GraphQL/gRPC/WebSocket) หรือรูปแบบ payload เชิงเทคนิคปรากฏในเนื้อหา ถ้า user พยายามระบุ protocol/รายละเอียดเทคนิคมาระหว่างทาง ให้แจ้งว่าเอกสารนี้จงใจไม่ผูกกับ tech stack และเสนอให้เก็บรายละเอียดนั้นไว้ทำเป็นเอกสารแยกภายหลังแทน

## ขั้นตอน

### 1. สำรวจข้อมูลต้นทาง

- Read `docs/01-requirements/backlog.md` และ `docs/01-requirements/feature-list.md` (ถ้ามี)
- Glob `docs/01-requirements/01-spec/*.md` (ยกเว้น `index.md`)
- Glob `docs/02-design/01-prototypes/*-journey.md`
- Glob `docs/02-design/02-technical/high-level-architecture.md` — Read ถ้ามี เพื่อดูองค์ประกอบ/data flow เป็นฐานระบุ operation
- Glob `docs/02-design/02-technical/database-schema.md` — Read ถ้ามี เพื่ออ้างอิงชื่อเอนทิตี/attribute ใน Input/Output ของ operation
- Glob `docs/02-design/02-technical/api-spec.md` เพื่อดูว่ามีไฟล์เดิมอยู่แล้วหรือไม่ (Read ถ้ามี เพื่อดูกรอบการจัดกลุ่ม/ประเด็นคลุมเครือที่เคยตัดสินใจไว้แล้ว)

### 2. แจ้ง user ถ้ายังไม่มี high-level-architecture.md หรือ database-schema.md

ถ้ายังไม่มีไฟล์ใดไฟล์หนึ่ง (หรือทั้งคู่) ให้แจ้ง user ว่าปกติควรมีเอกสารเหล่านี้ก่อนเพื่อให้ operation อ้างอิงองค์ประกอบ/เอนทิตีที่นิยามไว้แล้วได้แม่นยำกว่า และเสนอทางเลือกว่าจะรัน skill `architecture` และ/หรือ `database-schema` ให้ก่อนหรือไม่ (ไม่บังคับ — ถ้า user อยากทำต่อจาก spec/journey ตรงเลยก็ทำได้ โดย operation จะใช้คำอธิบายเชิงธุรกิจแทนการอ้างอิง entity ที่นิยามไว้แล้ว)

### 3. กำหนดกรอบการจัดกลุ่ม operation — ถามเสมอถ้ายังไม่เคยตัดสินใจไว้

ถ้าไฟล์เดิมยังไม่มี หรือยังไม่เคยระบุกรอบไว้ชัดเจน ให้ AskUserQuestion พร้อมตัวเลือกอย่างน้อย 3 แบบ พร้อมข้อดี/ข้อเสีย เช่น:

1. **จัดกลุ่มตามเอนทิตี/โดเมนข้อมูล** (เช่น operation ทั้งหมดที่เกี่ยวกับ "ออเดอร์" อยู่กลุ่มเดียวกัน) — ข้อดี: สอดคล้องกับ database-schema.md โดยตรง หาง่ายว่าเอนทิตีหนึ่งมี operation อะไรบ้าง; ข้อเสีย: operation ที่ข้ามหลายเอนทิตีในทีเดียว (เช่น flow ที่กระทบทั้งออเดอร์และเมนู) อาจต้องเลือกว่าใส่ไว้กลุ่มไหน
2. **จัดกลุ่มตามบทบาทผู้ใช้ (Actor)** (เช่น operation ทั้งหมดที่ลูกค้าเรียกใช้ อยู่กลุ่มเดียวกัน) — ข้อดี: อ่านง่ายจากมุมมอง "บทบาทนี้ทำอะไรได้บ้าง" เหมาะเวลาออกแบบสิทธิ์การเข้าถึง; ข้อเสีย: operation ที่ใช้ร่วมกันหลายบทบาทอาจถูกกระจายซ้ำในหลายกลุ่ม
3. **จัดกลุ่มตาม user journey** (เช่น operation ทั้งหมดที่เกิดขึ้นใน journey เดียวกันอยู่ด้วยกันตามลำดับ) — ข้อดี: เห็นลำดับการเรียก operation จริงตามการใช้งาน ต่อยอดจาก journey ที่มีอยู่แล้วได้ตรงไปตรงมา; ข้อเสีย: operation ที่ถูกใช้ข้าม journey หลายอันอาจถูกกระจายซ้ำในหลายกลุ่ม

ถ้า user เลือกไม่ถูก ให้แนะนำ default เป็นตัวเลือก 1 (ตามเอนทิตี/โดเมน) เมื่อมี `database-schema.md` อยู่แล้ว เพราะเชื่อมโยงกันตรงที่สุด และแนะนำตัวเลือก 3 (ตาม journey) เมื่อยังไม่มี database-schema.md หรือระบบยังเน้นอธิบายเชิง flow การใช้งานมากกว่า

### 4. เคลียร์ประเด็น operation อื่นที่ spec ยังไม่ระบุชัดเจน — ถามเมื่อจำเป็น

ตรวจสอบ backlog/spec/journey ว่ามีประเด็นที่กระทบการออกแบบ operation แต่ยังไม่ถูกระบุไว้หรือไม่ เช่น:

- operation บางตัวต้องทำงานแบบทันที (synchronous เชิงแนวคิด) หรือทำงานเบื้องหลังได้ (asynchronous เชิงแนวคิด)
- operation บางตัวต้องรองรับการเรียกซ้ำอย่างปลอดภัย (idempotent เชิงแนวคิด) หรือไม่ เช่น กรณีเครือข่ายขัดข้องแล้วเรียกซ้ำ
- ขอบเขตสิทธิ์การเข้าถึงของแต่ละ operation ที่ spec ยังไม่ระบุชัดเจน

ถ้าประเด็นไหนกระทบการออกแบบ operation อย่างมีนัยสำคัญและยังไม่ชัดเจน ให้ AskUserQuestion ถามพร้อมตัวเลือกอย่างน้อย 3 แบบต่อประเด็น (พร้อมข้อดี/ข้อเสีย) ถ้าไม่มีประเด็นแบบนี้ที่กระทบอย่างมีนัยสำคัญ ให้ข้ามขั้นตอนนี้ไปได้เลย

### 5. ส่งงานให้ subagent `api-spec-writer`

เรียก Agent tool ด้วย `subagent_type: "api-spec-writer"` (foreground เพื่อรอผลก่อนตอบ user) พร้อมส่ง:

- วันที่ปัจจุบัน (YYYY-MM-DD)
- กรอบการจัดกลุ่ม operation ที่ตกลงในขั้นตอน 3
- ขอบเขต backlog/spec/journey ทั้งหมดที่ต้องครอบคลุม (ปกติคือทุกรายการที่มีอยู่ในปัจจุบัน)
- คำตอบทั้งหมดจากขั้นตอน 4 (ถ้ามี) หรือระบุว่า "ไม่มีประเด็นเพิ่มเติมนอกจาก spec ที่มีอยู่"
- หมายเหตุว่ามี/ไม่มี `high-level-architecture.md` และ `database-schema.md` ให้อ้างอิง (จากขั้นตอน 2)

### 6. รายงานผลกลับ user

สรุป path ไฟล์ api-spec.md, operation ที่ครอบคลุมในรอบนี้, และประเด็นที่ยังค้างเป็น open question (ถ้ามี) พร้อมชวน user เพิ่มข้อมูลได้ภายหลังด้วยการรัน `/api-spec` ซ้ำเมื่อมี requirement ใหม่

## หมายเหตุ

- ไฟล์ `docs/02-design/02-technical/api-spec.md` เป็น living document เดียวของทั้งโปรเจกต์ — อัปเดตทับเนื้อหาหลักเสมอ แต่คงหัวข้อ "ประวัติการแก้ไข" ท้ายไฟล์ไว้ (ต่อท้าย ไม่ลบของเดิม)
- เมื่อทีมเลือก protocol จริงแล้ว ให้สร้างเอกสารแยกต่างหากสำหรับ API design เชิงเทคนิค อย่านำรายละเอียด protocol มาผสมในไฟล์นี้
