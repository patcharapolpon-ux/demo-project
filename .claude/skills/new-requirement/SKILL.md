# New Requirement — จาก requirement ดิบ สู่เอกสาร spec + backlog + log

Skill นี้ทำงานใน main conversation (เพื่อให้ถามคำถาม user แบบโต้ตอบได้) แล้วค่อยส่งงานเขียนไฟล์ให้ subagent `requirement-writer` ทำในขั้นตอนสุดท้าย

## ขั้นตอน

### 1. รับ requirement ดิบ

ถ้า user ยังไม่ได้อธิบาย requirement มาในข้อความ ให้ถามสั้น ๆ ว่าต้องการบันทึก requirement เรื่องอะไร

### 2. ตรวจสอบความชัดเจน — ถามเมื่อไม่แน่ใจ

พิจารณา requirement ที่ได้ตามมิติเหล่านี้เป็นอย่างน้อย: ขอบเขต (in/out of scope), ผู้ใช้/บทบาทที่เกี่ยวข้อง, กฎทางธุรกิจ/เงื่อนไข edge case, ข้อมูลที่เกี่ยวข้อง, ความสำคัญ/ลำดับก่อนหลัง

ถ้ามีจุดใดที่ไม่ชัดเจนหรือตีความได้หลายแบบ **ห้ามเดาเอง** ให้ใช้ AskUserQuestion ถาม โดยทุกคำถามต้องมีตัวเลือกแนวทางให้เลือกอย่างน้อย 3 แนวทาง (ไม่นับตัวเลือก "Other" ที่ระบบเพิ่มให้อัตโนมัติ) เช่น ถ้าไม่ชัดเรื่องขอบเขต อาจเสนอ "ทำเฉพาะ X", "ทำ X และ Y", "ทำทั้งระบบแบบครบวงจร" ให้เลือก ทำซ้ำขั้นตอนนี้จนกว่า requirement จะชัดเจนพอจะเขียนเอกสารได้

### 3. ตรวจสอบว่ามีเอกสารเดิมที่เกี่ยวข้องหรือไม่

ใช้ Grep ค้นหาคร่าว ๆ ในโฟลเดอร์ `docs/01-requirements/01-spec/` ด้วย keyword หลักของ requirement ใหม่

- ถ้าไม่พบสิ่งที่เกี่ยวข้อง → ไปขั้นตอน 4 (สร้างเอกสารใหม่)
- ถ้าพบเอกสารที่เนื้อหาเกี่ยวข้อง/ทับซ้อนกัน แต่ยังไม่ชัดว่าควรสร้างเอกสารใหม่แยกหรือแก้ไขของเดิม ให้ใช้ AskUserQuestion ถาม user พร้อมตัวเลือกอย่างน้อย 3 แบบ เช่น:
  1. สร้างเอกสารใหม่แยกต่างหาก (เพราะเป็นเรื่องคนละส่วนกัน)
  2. แก้ไข/เพิ่มเนื้อหาในเอกสารเดิม (เพราะเป็นการต่อยอด/แก้ไขเรื่องเดียวกัน)
  3. สร้างเอกสารใหม่ แต่ใส่ wikilink อ้างอิงถึงเอกสารเดิมไว้ (เพราะเกี่ยวข้องกันแต่แยกเรื่องพอสมควร)

### 4. ส่งงานให้ subagent `requirement-writer`

เมื่อ requirement ชัดเจนและตัดสินใจเรื่องสร้างใหม่/แก้ไขเดิมแล้ว ให้เรียก Agent tool ด้วย `subagent_type: "requirement-writer"` (รันแบบ foreground เพื่อรอผลก่อนตอบ user) พร้อมส่งข้อมูลต่อไปนี้ไปในพรอมต์:

- requirement ฉบับสรุปที่ชัดเจนแล้ว (ภาษาไทย) รวมคำตอบทั้งหมดที่ user ให้มาในขั้นตอน 2
- วันที่ปัจจุบัน (YYYY-MM-DD)
- หัวข้อสรุปสั้น ๆ สำหรับตั้งชื่อไฟล์ (slug ภาษาอังกฤษ)
- ผลการตรวจสอบเอกสารเดิมจากขั้นตอน 3 และการตัดสินใจของ user (สร้างใหม่ / แก้ไขเดิม / สร้างใหม่พร้อมลิงก์อ้างอิง)

### 5. รายงานผลกลับ user

สรุปให้ user ทราบแบบกระชับ: path ไฟล์ spec ที่ถูกสร้าง/แก้ไข, สรุปว่า backlog.md และ log ของวันนี้ถูกอัปเดตแล้ว, และเอกสารเดิมที่เกี่ยวข้อง (ถ้ามี)

## หมายเหตุ

- Path ของ log ที่ใช้จริงคือ `docs/05-log/{YYYYMMDD}-log.md` (โฟลเดอร์ log จริงในโปรเจกต์นี้คือ `05-log/`)
- ห้ามลบเอกสารเดิมเด็ดขาด — ถ้าเอกสารเดิมถูกแทนที่ทั้งหมด ให้แจ้ง user และเสนอย้ายไป `docs/00-archived/` แทน (อย่าย้ายเองโดยไม่ถาม)
