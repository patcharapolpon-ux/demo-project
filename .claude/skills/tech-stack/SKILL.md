# Tech Stack — สัมภาษณ์เพื่อเลือก และสร้าง/อัปเดตเอกสาร Tech Stack

Skill นี้ทำงานใน main conversation ทั้งหมด (สำรวจแหล่งข้อมูล, สัมภาษณ์ user แบบเข้มข้นทุกมิติที่ยังไม่ชัดเจน, สังเคราะห์เป็น 3 แนวทาง stack ให้เลือก) แล้วค่อยส่งงานเขียนไฟล์ให้ subagent `tech-stack-writer` ทำในขั้นตอนสุดท้ายเท่านั้น ไฟล์ผลลัพธ์เป็น **living document เดียวต่อโปรเจกต์** เหมือน `architecture`/`test-plan`

**กติกาที่ต้องคุมตลอด skill นี้:** เอกสารนี้คือจุดเดียวในโปรเจกต์ที่**ตั้งใจให้ผูกมัดกับเทคโนโลยีจริง** — ตรงข้ามกับ `architecture`/`database-schema`/`api-spec`/`detailed-design` ที่ห้ามระบุเทคโนโลยี ห้ามข้ามขั้นตอนสัมภาษณ์แล้วเดา stack เอง ทุกมิติที่ไม่ชัดเจนต้องถาม user ก่อนเสมอ พร้อมตัวเลือก/แนวทางอย่างน้อย 3 แบบและข้อดี-ข้อเสียของแต่ละแบบ เพื่อให้ user ตัดสินใจเองได้

## ขั้นตอน

### 1. สำรวจข้อมูลต้นทาง

- Read `docs/01-requirements/backlog.md` และ `docs/01-requirements/feature-list.md` (ถ้ามี)
- Read `docs/02-design/02-technical/high-level-architecture.md` (ถ้ามี) — ดูองค์ประกอบเชิงแนวคิดและข้อจำกัด/สมมติฐาน (เช่น real-time, หลายสาขา, offline) ที่เคยตอบไว้แล้ว เพื่อไม่ถามซ้ำ
- Read `docs/02-design/02-technical/database-schema.md` (ถ้ามี) — ดูลักษณะเอนทิตี/ความสัมพันธ์ เพื่อประกอบการถามเรื่อง relational vs document
- Read `docs/02-design/02-technical/api-spec.md` (ถ้ามี) — ดูกลุ่ม operation เพื่อประกอบการแนะนำ backend framework
- Read `docs/03-testing/01-test-plan/test-plan.md` (ถ้ามี) — ดึง NFR (performance/security/availability) ที่เคยรวบรวมไว้แล้ว เพื่อไม่ถามซ้ำ
- Glob `docs/02-design/02-technical/tech-stack.md` — ถ้ามีไฟล์เดิม Read เพื่อดูว่าเกณฑ์/stack เดิมเป็นอย่างไร และถามเฉพาะส่วนที่เปลี่ยนแปลง/ยังไม่ตอบ

ถ้า `high-level-architecture.md` หรือ `database-schema.md` ยังไม่มี ให้แจ้ง user ว่าคำแนะนำ stack จะแม่นยำน้อยกว่า (ไม่มีองค์ประกอบ/เอนทิตีให้ map) และเสนอว่าจะรัน `/architecture` และ/หรือ `/database-schema` ให้ก่อนหรือจะดำเนินการเลย (ไม่บังคับ)

### 2. สัมภาษณ์แบบเข้มข้น — ถามทุกมิติที่ยังไม่มีคำตอบจากเอกสารต้นทาง

ถามเป็นชุดคำถามผ่าน `AskUserQuestion` (แบ่งเป็นหลายรอบได้ รอบละไม่เกิน 4 คำถาม) ครอบคลุมมิติต่อไปนี้เป็นอย่างน้อย — **ข้ามมิติที่มีคำตอบชัดเจนอยู่แล้วในเอกสารต้นทางหรือไฟล์ tech-stack.md เดิม** แต่ถ้าไม่ชัดเจนหรือไม่มีอยู่เลย ต้องถามเสมอ ห้ามเดาแทน user ทุกคำถามต้องมีตัวเลือกอย่างน้อย 3 แบบพร้อมข้อดี/ข้อเสียของแต่ละแบบ:

1. **ความเชี่ยวชาญ/ความถนัดของทีม** เช่น
   - ทีมถนัด JavaScript/TypeScript ทั้ง frontend-backend — ข้อดี: เรียนภาษาเดียวจบทั้ง stack, ecosystem/ตัวอย่างเยอะ; ข้อเสีย: performance งานคำนวณหนักด้อยกว่าภาษาอื่นบางกลุ่ม
   - ทีมถนัด Python — ข้อดี: อ่านง่าย เหมาะกับทีมที่เพิ่งเริ่ม, library ด้าน data/ML พร้อม; ข้อเสีย: concurrency/performance ต้องดูแลเพิ่มถ้า traffic สูง
   - ทีมยังไม่ถนัดภาษาไหนเป็นพิเศษ/เป็นนักศึกษาที่กำลังเรียน — ข้อดี: เลือกได้อิสระตามความเหมาะสมกับโปรเจกต์; ข้อเสีย: มี learning curve เพิ่มไม่ว่าจะเลือกทางไหน
2. **งบประมาณ/ต้นทุน hosting ที่ยอมรับได้** เช่น
   - ต้องการ free-tier/ต้นทุนต่ำที่สุด (โปรเจกต์วิชาเรียน/งบจำกัด) — ข้อดี: ไม่มีความเสี่ยงด้านค่าใช้จ่าย; ข้อเสีย: มีข้อจำกัดด้าน resource/traffic ของ free-tier
   - มีงบเล็กน้อยสำหรับ hosting รายเดือน — ข้อดี: เลือก service ได้กว้างขึ้น เสถียรกว่า free-tier; ข้อเสีย: ต้องมีคนดูแล/จ่ายบิลต่อเนื่อง
   - งบเปิด ไม่กังวลต้นทุนช่วงแรก — ข้อดี: เลือก stack ตามความเหมาะสมทางเทคนิคได้เต็มที่; ข้อเสีย: ถ้าไม่ควบคุม อาจมีต้นทุนเกินจำเป็นสำหรับ scale จริง
3. **กรอบเวลาที่ต้องส่งมอบ/เห็นระบบทำงานจริง** เช่น
   - ต้องรีบ ต้องการ stack ที่ setup เร็ว มี boilerplate/ตัวช่วยพร้อมใช้ — ข้อดี: เห็นผลเร็ว; ข้อเสีย: อาจเลือก tool ที่ไม่ optimal ในระยะยาว
   - มีเวลาปานกลาง พอศึกษา stack ใหม่ได้บ้าง — ข้อดี: เลือกได้สมดุลระหว่างความเร็วกับความเหมาะสม; ข้อเสีย: —
   - ไม่เร่ง เน้นความถูกต้อง/คุณภาพของสถาปัตยกรรมมากกว่าความเร็ว — ข้อดี: มีเวลาเลือก/ทดสอบ stack ให้เหมาะสมที่สุด; ข้อเสีย: ใช้เวลานานกว่าจะได้ระบบ deploy จริง
4. **Platform เป้าหมายที่ผู้ใช้จะเข้าถึงระบบ** เช่น
   - Web app (browser) เท่านั้น — ข้อดี: พัฒนา/ดูแล codebase เดียว เข้าถึงง่ายทุกอุปกรณ์ที่มี browser; ข้อเสีย: experience ด้อยกว่า native app บนมือถือ
   - Web + Mobile app (ต้องมี native/hybrid app) — ข้อดี: experience บนมือถือดีกว่า รองรับ feature เฉพาะอุปกรณ์ (เช่น พิมพ์ใบเสร็จผ่าน Bluetooth); ข้อเสีย: ต้องดูแลหลาย codebase/แพลตฟอร์มเพิ่ม
   - ต้องมีหน้าจอเฉพาะหน้าร้าน (POS/จอครัว) ร่วมกับ web/mobile — ข้อดี: ตอบโจทย์ operation หน้าร้านโดยตรง; ข้อเสีย: ซับซ้อนขึ้น ต้องดูแลอุปกรณ์ฮาร์ดแวร์เพิ่ม

ถ้า `high-level-architecture.md` ระบุ constraint เรื่อง real-time/หลายสาขา/offline ไว้แล้ว ให้นำมาสรุปให้ user ยืนยันอีกครั้งว่ายังใช้ได้อยู่ (ไม่ต้องถามใหม่ทั้งหมด) แต่ถ้ายังไม่มีข้อมูลเรื่องนี้เลย ให้ถามเพิ่มในชุดคำถามนี้ด้วย

ต่อด้วยชุดคำถามรอบถัดไป ครอบคลุมมิติที่เหลือ:

5. **ลักษณะข้อมูล/การเข้าถึงข้อมูล** (อ้างอิง database-schema.md ถ้ามี) เช่น
   - ข้อมูลมีโครงสร้างชัดเจน ต้อง join/รักษาความถูกต้องข้ามเอนทิตีเข้มงวด (เชิง relational) — ข้อดี: ACID, ความถูกต้องของข้อมูลสูง, query ซับซ้อนทำได้ดี; ข้อเสีย: scale แนวนอนยากกว่า, schema เปลี่ยนบ่อยจะลำบาก
   - ข้อมูลแต่ละเอนทิตีค่อนข้างอิสระ โครงสร้างเปลี่ยนบ่อย (เชิง document/NoSQL) — ข้อดี: schema ยืดหยุ่น, scale แนวนอนง่าย; ข้อเสีย: join ข้ามเอนทิตีทำได้จำกัด, ต้องดูแล data consistency เอง
   - ผสมทั้งสองแบบตามความเหมาะสมของแต่ละเอนทิตี — ข้อดี: ได้ข้อดีของทั้งสองฝั่ง; ข้อเสีย: ซับซ้อนขึ้น ต้องดูแล 2 ระบบข้อมูล
6. **ความคุ้นเคยด้าน deploy/DevOps ของทีม** เช่น
   - ต้องการ managed/PaaS ที่ deploy ง่ายที่สุด ไม่อยากดูแล server เอง — ข้อดี: ลดงานดูแล infrastructure; ข้อเสีย: ปรับแต่งเชิงลึกได้จำกัดกว่า, อาจมีค่าใช้จ่ายต่อหน่วยสูงกว่าที่ scale ใหญ่
   - คุ้นเคย container/Docker พอประมาณ — ข้อดี: portable, ควบคุม environment ได้มากขึ้น; ข้อเสีย: ต้องมีความรู้พื้นฐาน container/orchestration
   - มีความสามารถดูแล infrastructure เอง (VM/Kubernetes) — ข้อดี: ควบคุมได้เต็มที่ ปรับ cost/performance ได้ละเอียด; ข้อเสีย: ต้องใช้เวลา/ความรู้ดูแลสูง

ถ้ามิติใดยังคลุมเครือเพิ่มเติมนอกเหนือจากที่ระบุ (เช่น ต้องการ integration พิเศษ เช่น payment gateway, printer, LINE Notify) ให้ถามเพิ่มด้วยรูปแบบเดียวกัน (>= 3 ตัวเลือกพร้อมข้อดี/ข้อเสีย)

### 3. สังเคราะห์เป็น 3 แนวทาง stack แล้วเสนอให้ user เลือก

จากคำตอบทั้งหมดในขั้นตอน 2 ให้สังเคราะห์เป็น**อย่างน้อย 3 แนวทาง tech stack แบบครบชุด** (ระบุ client/backend/database/infrastructure คร่าว ๆ ในแต่ละแนวทาง) ที่ตอบโจทย์เกณฑ์ที่ user ให้ไว้ในระดับความเข้มข้นต่างกัน (เช่น แนวทางที่เน้นเรียบง่าย/ต้นทุนต่ำสุด, แนวทางที่สมดุล, แนวทางที่เน้นความสามารถขยายสเกล/ฟีเจอร์เต็มที่สุด) แล้ว AskUserQuestion ให้ user เลือก 1 แนวทาง หรือระบุว่าต้องการ mix ปรับจากหลายแนวทาง — ต้องมีข้อดี/ข้อเสียของแต่ละแนวทางประกอบการเลือกเสมอ

ตัวอย่างโครง (ปรับเนื้อหาจริงตามคำตอบที่ได้จากขั้นตอน 2 เสมอ ห้ามใช้ตัวอย่างนี้ตรง ๆ โดยไม่ปรับ):

1. **แนวทางเรียบง่าย/ต้นทุนต่ำ** — เช่น full-stack framework เดียวที่ทีมถนัดอยู่แล้ว + managed database ระดับ free/starter tier + PaaS hosting เดียวจบ — ข้อดี: setup เร็ว ต้นทุนต่ำ เหมาะกับ timeline สั้น/งบจำกัด; ข้อเสีย: จำกัดด้าน scale และ feature เฉพาะทาง (เช่น native mobile)
2. **แนวทางสมดุล** — เช่น แยก frontend/backend framework ตามความถนัดทีม + relational/document database ตามลักษณะข้อมูลจริง + container-based hosting ระดับกลาง — ข้อดี: สมดุลระหว่างความเร็วในการพัฒนากับความสามารถขยายสเกลในอนาคต; ข้อเสีย: ต้องดูแล component มากกว่าแนวทางที่ 1 เล็กน้อย
3. **แนวทางเน้นขยายสเกล/ฟีเจอร์เต็มรูปแบบ** — เช่น backend แยก service ตาม domain + database ผสม (relational + document ตามเอนทิตี) + infrastructure ที่ทีมดูแลเอง (container orchestration) + native mobile app แยกจาก web — ข้อดี: รองรับการเติบโต/ฟีเจอร์เฉพาะทาง (offline, หลายสาขา) ได้ดีที่สุด; ข้อเสีย: ซับซ้อนสูงสุด ใช้เวลา/ความรู้ทีมมากที่สุด

### 4. ส่งงานให้ subagent `tech-stack-writer`

เรียก Agent tool ด้วย `subagent_type: "tech-stack-writer"` (foreground เพื่อรอผลก่อนตอบ user) พร้อมส่ง:

- วันที่ปัจจุบัน (YYYY-MM-DD)
- เกณฑ์การเลือกทั้งหมดจากขั้นตอน 2 (สรุปทุกมิติ)
- 3 แนวทางที่เสนอไปในขั้นตอน 3 (พร้อมข้อดี/ข้อเสียของแต่ละแนวทาง) และแนวทางที่ user เลือกจริง (หรือรายละเอียด mix ที่ user ปรับ)
- stack ที่เลือกจริงแยกตาม layer ให้ชัดเจนที่สุดเท่าที่มีข้อมูล (ถ้า layer ไหนยังไม่ระบุ ให้บอกตรง ๆ ว่ายังไม่ตัดสินใจ)

### 5. รายงานผลกลับ user

สรุป path ไฟล์ tech-stack.md, stack ที่เลือกทีละ layer, และประเด็นที่ยังค้างเป็น open question (ถ้ามี) พร้อมชวน user เพิ่ม/ปรับข้อมูลได้ภายหลังด้วยการรัน `/tech-stack` ซ้ำเมื่อมีเกณฑ์การเลือกเปลี่ยนไป

## หมายเหตุ

- ไฟล์ `docs/02-design/02-technical/tech-stack.md` เป็น living document เดียวของทั้งโปรเจกต์ — อัปเดตทับเนื้อหาหลักเสมอ แต่คงหัวข้อ "ประวัติการแก้ไข" ท้ายไฟล์ไว้ (ต่อท้าย ไม่ลบของเดิม)
- ต่างจาก `architecture`/`database-schema`/`api-spec`/`detailed-design` ตรงที่ skill/agent คู่นี้**ต้องระบุเทคโนโลยีจริง** — ถ้า user พยายามให้เอกสารนี้ยังเป็นเชิงแนวคิดอยู่ (ไม่ระบุเทคโนโลยี) ให้แจ้งว่าไม่ตรงจุดประสงค์ของเอกสารนี้ และแนะนำว่าประเด็นเชิงแนวคิดควรอยู่ใน `high-level-architecture.md` แทน
- ห้ามข้ามการสัมภาษณ์ไปเดา stack เองแม้ user จะเร่งให้ทำเร็ว ๆ — อย่างน้อยต้องเคลียร์มิติหลักทั้ง 6 ข้อในขั้นตอน 2 ก่อนเสนอ 3 แนวทางเสมอ เว้นแต่มีคำตอบอยู่แล้วในเอกสารต้นทาง/ไฟล์เดิม
