# Database Schema — สร้าง/อัปเดต Database Schema เชิงแนวคิด

Skill นี้ทำงานใน main conversation ทั้งหมด (สำรวจแหล่งข้อมูล, กำหนดแนวทางการแตกเอนทิตี, เคลียร์ประเด็นคลุมเครือ) แล้วค่อยส่งงานเขียนไฟล์ให้ subagent `database-schema-writer` ทำในขั้นตอนสุดท้ายเท่านั้น ไฟล์นี้เป็น **living document เดียวต่อโปรเจกต์** เหมือน `architecture`/`test-plan` ไม่มีขั้นตอนกำหนดขอบเขตเฉพาะบางรายการเหมือน acceptance-criteria/test-case เพราะแบบจำลองข้อมูลต้องมองภาพรวมทั้งระบบเสมอ (เอนทิตีอ้างอิงถึงกันข้าม feature)

**กติกาที่ต้องคุมตลอด skill นี้:** เอกสารผลลัพธ์ต้องเป็นแบบจำลองข้อมูลเชิงแนวคิด (conceptual) เท่านั้น ห้ามมีชื่อฐานข้อมูล เทคโนโลยี หรือชนิดข้อมูลเฉพาะของ DBMS ปรากฏในเนื้อหา ถ้า user พยายามระบุ DBMS/ชนิดข้อมูลจริงมาระหว่างทาง ให้แจ้งว่าเอกสารนี้จงใจไม่ผูกกับ tech stack และเสนอให้เก็บรายละเอียดนั้นไว้ทำเป็นเอกสารแยกภายหลังแทน

เอกสารนี้เป็นการ**ขยายรายละเอียด**จากหัวข้อ "แบบจำลองข้อมูลเชิงแนวคิด" ที่มีอยู่แล้วใน `high-level-architecture.md` (ถ้ามี) — ไม่ใช่การแทนที่ ทั้งสองไฟล์อยู่แยกกันและลิงก์ไป-กลับ ห้ามลบ/แก้ตารางเอนทิตีสรุปในไฟล์ architecture

## ขั้นตอน

### 1. สำรวจข้อมูลต้นทาง

- Read `docs/01-requirements/backlog.md` และ `docs/01-requirements/feature-list.md` (ถ้ามี)
- Glob `docs/01-requirements/01-spec/*.md` (ยกเว้น `index.md`)
- Glob `docs/02-design/01-prototypes/*-journey.md`
- Glob `docs/02-design/02-technical/high-level-architecture.md` — Read ถ้ามี เพื่อดูหัวข้อ "แบบจำลองข้อมูลเชิงแนวคิด" เป็นจุดเริ่มต้น
- Glob `docs/02-design/02-technical/database-schema.md` เพื่อดูว่ามีไฟล์เดิมอยู่แล้วหรือไม่ (Read ถ้ามี เพื่อดูแนวทางแตกเอนทิตี/ประเด็นคลุมเครือที่เคยตัดสินใจไว้แล้ว)
- Glob `docs/02-design/02-technical/tech-stack.md` — ถ้ามี ให้ Read เพื่อเตรียมส่งต่อ subagent สำหรับเขียนหัวข้อ "Technical Mapping" ท้ายไฟล์ (ไม่ต้องถาม user อะไรเพิ่มสำหรับส่วนนี้ เพราะเป็นการอ้างอิงการตัดสินใจที่มีอยู่แล้ว ไม่ใช่ประเด็นคลุมเครือใหม่)

### 2. แจ้ง user ถ้ายังไม่มี high-level-architecture.md

ถ้ายังไม่มี `docs/02-design/02-technical/high-level-architecture.md` ให้แจ้ง user ว่าปกติเอกสารนี้ควรมีก่อน (มีรายชื่อเอนทิตี+ความสัมพันธ์ระดับสรุปให้ต่อยอด) และเสนอทางเลือกว่าจะรัน skill `architecture` ให้ก่อนหรือไม่ (ไม่บังคับ — ถ้า user อยากให้ระบุเอนทิตีจาก backlog/spec ตรงเลยก็ทำได้)

### 3. กำหนดแนวทางการแตกเอนทิตี (normalization framing) — ถามเสมอถ้ายังไม่เคยตัดสินใจไว้

ถ้าไฟล์เดิมยังไม่มี หรือยังไม่เคยระบุแนวทางไว้ชัดเจน ให้ AskUserQuestion พร้อมตัวเลือกอย่างน้อย 3 แบบ พร้อมข้อดี/ข้อเสีย เช่น:

1. **แตกละเอียดตามหลัก 1 fact ต่อเอนทิตี** (normalized เชิงแนวคิด) — ข้อดี: ไม่มีข้อมูลซ้ำซ้อนเชิงแนวคิด, ความสัมพันธ์ชัดเจน, ต่อยอดไป schema จริงได้ตรงไปตรงมา; ข้อเสีย: จำนวนเอนทิตีอาจมากเกินความจำเป็นถ้าระบบยังเล็ก
2. **จัดกลุ่มตามการใช้งานจริงแบบ denormalized เชิงแนวคิด** (เช่น embed รายการย่อยไว้ใน attribute ของเอนทิตีหลักเมื่อไม่มีความจำเป็นต้อง query แยก) — ข้อดี: จำนวนเอนทิตีน้อย อ่านง่าย ตรงกับวิธีใช้งานจริง; ข้อเสีย: ถ้าภายหลังต้อง query/แก้ไขข้อมูลย่อยแยกจากเอนทิตีหลัก จะต้องออกแบบใหม่บางส่วน
3. **ระบุแค่เอนทิตีหลักและความสัมพันธ์ระดับสรุป ไม่ลงรายละเอียด attribute ที่เป็น list ซับซ้อน** — ข้อดี: ทำเร็ว เหมาะกับช่วงต้นโปรเจกต์ที่ยังไม่แน่ใจรายละเอียด; ข้อเสีย: ทีมพัฒนาต้องกลับมาเติมรายละเอียดเพิ่มก่อนเริ่ม implement จริง

ถ้า user เลือกไม่ถูก ให้แนะนำ default เป็นตัวเลือก 1 (normalized) เพราะสอดคล้องกับหลักการออกแบบข้อมูลทั่วไปและลด rework ตอนออกแบบ schema จริงในอนาคต

### 4. เคลียร์ประเด็นแบบจำลองข้อมูลอื่นที่ spec ยังไม่ระบุชัดเจน — ถามเมื่อจำเป็น

ตรวจสอบ backlog/spec/journey ว่ามีประเด็นที่กระทบโครงสร้างข้อมูลแต่ยังไม่ถูกระบุไว้หรือไม่ เช่น:

- เอนทิตีบางตัวควรแยกจากกันหรือรวมกัน (เช่น "ตัวเลือกเสริมของสินค้าในออเดอร์" ควรเป็นเอนทิตีแยกที่มีความสัมพันธ์ของตัวเอง หรือเป็น attribute แบบ list ฝังอยู่ในเอนทิตีหลัก)
- ข้อมูลบางประเภทต้องเก็บประวัติ/versioning เชิงแนวคิดหรือไม่ (เช่น ราคาสินค้าที่เปลี่ยนไปตามเวลา ต้องเก็บราคา ณ ขณะสั่งไว้ในออเดอร์ด้วยหรือไม่)
- นโยบายอายุ/การลบข้อมูลของเอนทิตีที่ spec ยังไม่ระบุชัดเจน

ถ้าประเด็นไหนกระทบโครงสร้างเอนทิตีอย่างมีนัยสำคัญและยังไม่ชัดเจน ให้ AskUserQuestion ถามพร้อมตัวเลือกอย่างน้อย 3 แบบต่อประเด็น (พร้อมข้อดี/ข้อเสีย) ถ้าไม่มีประเด็นแบบนี้ที่กระทบอย่างมีนัยสำคัญ ให้ข้ามขั้นตอนนี้ไปได้เลย

### 5. ส่งงานให้ subagent `database-schema-writer`

เรียก Agent tool ด้วย `subagent_type: "database-schema-writer"` (foreground เพื่อรอผลก่อนตอบ user) พร้อมส่ง:

- วันที่ปัจจุบัน (YYYY-MM-DD)
- แนวทางการแตกเอนทิตีที่ตกลงในขั้นตอน 3
- ขอบเขต backlog/spec/journey ทั้งหมดที่ต้องครอบคลุม (ปกติคือทุกรายการที่มีอยู่ในปัจจุบัน)
- คำตอบทั้งหมดจากขั้นตอน 4 (ถ้ามี) หรือระบุว่า "ไม่มีประเด็นเพิ่มเติมนอกจาก spec ที่มีอยู่"
- หมายเหตุว่ามี/ไม่มี `docs/02-design/02-technical/tech-stack.md` ให้อ้างอิง ถ้ามีให้ส่งชื่อ DBMS ที่เลือกไปด้วย (สำหรับเขียนหัวข้อ "Technical Mapping" ท้ายไฟล์)

### 6. รายงานผลกลับ user

สรุป path ไฟล์ database-schema.md, เอนทิตีที่ครอบคลุมในรอบนี้, และประเด็นที่ยังค้างเป็น open question (ถ้ามี) พร้อมชวน user เพิ่มข้อมูลได้ภายหลังด้วยการรัน `/database-schema` ซ้ำเมื่อมี requirement ใหม่

## หมายเหตุ

- ไฟล์ `docs/02-design/02-technical/database-schema.md` เป็น living document เดียวของทั้งโปรเจกต์ — อัปเดตทับเนื้อหาหลักเสมอ แต่คงหัวข้อ "ประวัติการแก้ไข" ท้ายไฟล์ไว้ (ต่อท้าย ไม่ลบของเดิม)
- เอกสารนี้แยกจาก `high-level-architecture.md` โดยตั้งใจ (ไม่ยุบรวม) — architecture.md คงหัวข้อเอนทิตีระดับสรุปไว้เหมือนเดิม ส่วน database-schema.md ขยายรายละเอียด attribute เต็ม ทั้งสองไฟล์ลิงก์ไป-กลับกัน
- เมื่อทีมเลือก DBMS จริงแล้ว (มี `tech-stack.md`) ให้เพิ่มได้แค่หัวข้อ "Technical Mapping" สรุป column/ชนิดข้อมูลจริงท้ายไฟล์ (ตามที่ระบุในขั้นตอน 5) ห้ามนำรายละเอียด DBMS อื่น เช่น index/migration มาผสมในหัวข้อ 1-5
