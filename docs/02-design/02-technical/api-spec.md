# API Spec (Conceptual)

**วันที่จัดทำ/อัปเดตล่าสุด:** 2026-08-23
**สถานะ:** ร่าง (Draft)

> เอกสารนี้เป็นสัญญาการทำงานเชิงแนวคิด (Conceptual Operation Contract) **ยังไม่ผูกมัดกับ protocol, HTTP method, URL path, หรือรูปแบบ payload เชิงเทคนิคใด ๆ** การเลือก protocol จริงและรายละเอียดเชิงเทคนิค (REST/GraphQL, error code, auth) จะถูกจัดทำแยกต่างหากเมื่อมีการตัดสินใจเรื่อง stack แล้ว

## 1. ภาพรวม (Overview)

เอกสารนี้ครอบคลุม operation ทั้งหมดที่ปรากฏใน backlog/spec/journey ทั้ง 4 requirement ที่มีอยู่ในปัจจุบัน (20260802-001 ถึง 20260802-004) จัดกลุ่มตามเอนทิตี/โดเมนข้อมูลที่นิยามไว้แล้วใน [[database-schema|database-schema.md]] ได้แก่ ออเดอร์, รายการสินค้าในออเดอร์, โต๊ะ, เมนู, ผู้ใช้/พนักงาน, บันทึกเหตุการณ์ (Audit Log Record) และความยินยอม (Consent Record) แต่ละ operation อ้างอิงกลับไปยัง spec และ journey ต้นทางเสมอ ไม่มี operation ที่ถูกเพิ่มขึ้นโดยไม่มีที่มาจากเอกสารต้นทาง

## 2. รายการ Operation

### 2.1 ออเดอร์

#### สั่งออเดอร์ (สร้างออเดอร์ใหม่)

- **คำอธิบาย:** ลูกค้ายืนยันสั่งเมนูพร้อมตัวเลือกเสริมจากหน้าจอสั่งอาหารของโต๊ะ ระบบสร้างออเดอร์ใหม่พร้อมรายการสินค้าในออเดอร์ แล้วส่งเข้าคิวบาริสต้าโดยตรงทันที (ไม่ผ่านพนักงานเสิร์ฟกดรับก่อน) สถานะเริ่มต้นของออเดอร์คือ "รับออเดอร์แล้ว"
- **ผู้เรียกใช้ (Actor):** ลูกค้า
- **เงื่อนไขก่อนทำงาน (Precondition):** โต๊ะที่สั่งต้องมีอยู่จริงในระบบ (ผ่านการเปิดหน้าสั่งอาหารจากการสแกน QR มาก่อน); เมนูทุกรายการที่เลือกต้องอยู่ในสถานะ "เปิดขาย" ณ ขณะยืนยันสั่ง

**ข้อมูลนำเข้า (Input):**

| Field | ชนิดข้อมูลเชิงแนวคิด | บังคับ/ไม่บังคับ | คำอธิบาย |
|---|---|---|---|
| โต๊ะที่สั่ง (รหัสโต๊ะ) | ข้อความ (อ้างอิงโต๊ะ) | บังคับ | โต๊ะที่ออเดอร์นี้ผูกอยู่ |
| รายการสินค้า[] | รายการของ (เมนูที่สั่ง, ขนาด, ร้อน/เย็น, ระดับความหวาน, ชนิดนม, ท็อปปิ้ง/เพิ่มช็อต, หมายเหตุ) | บังคับ | รายการเมนูที่ลูกค้าเลือก พร้อมตัวเลือกเสริมครบทุกมิติต่อรายการ |
| ค่าระบุคำขอซ้ำเชิงแนวคิด (idempotency key เชิงแนวคิด) | ข้อความ (รหัสอ้างอิงคำขอ) | บังคับ | ค่ากำกับคำขอสั่งออเดอร์นี้ ใช้ตรวจว่าคำขอเดิมถูกส่งซ้ำหรือไม่ |

**ผลลัพธ์ (Output):**

| Field | ชนิดข้อมูลเชิงแนวคิด | คำอธิบาย |
|---|---|---|
| รหัสออเดอร์ | ข้อความ (รหัสอ้างอิง) | ตัวระบุเฉพาะของออเดอร์ที่สร้าง (หรือออเดอร์แรกที่สร้างไปแล้ว หากเป็นคำขอซ้ำ) |
| สถานะออเดอร์ | ค่าเลือกจากรายการ | สถานะเริ่มต้น "รับออเดอร์แล้ว" |
| รายการสินค้าในออเดอร์ที่บันทึก[] | รายการของ | รายการสินค้าที่บันทึกจริง พร้อมราคา ณ ขณะสั่ง (price snapshot) ของแต่ละรายการ |
| เวลาที่สั่ง | วันที่/เวลา | เวลาที่ยืนยันสั่งสำเร็จ |

**กฎธุรกิจ/การตรวจสอบ (Business Rules):** operation นี้ต้อง idempotent เชิงแนวคิด — ถ้าเรียกซ้ำด้วยค่าระบุคำขอซ้ำเดิม ต้องไม่สร้างออเดอร์ใหม่ซ้ำ แต่คืนผลลัพธ์ของออเดอร์แรกที่สร้างไปแล้วแทน; ออเดอร์ที่สร้างสำเร็จต้องเข้าคิวบาริสต้าโดยตรงทันทีโดยไม่ผ่านพนักงานเสิร์ฟกดรับก่อน; ราคาแต่ละรายการต้องบันทึกเป็น price snapshot ณ ขณะสั่ง ไม่เปลี่ยนตามราคาปัจจุบันของเมนูในอนาคต; การสร้างออเดอร์สำเร็จต้องกระตุ้นให้เกิดบันทึกเหตุการณ์ประเภท "สร้างออเดอร์ใหม่"

**กรณีผิดพลาดเชิงธุรกิจ (Business Exceptions):** ถ้าโต๊ะที่ระบุไม่มีอยู่จริง -> ปฏิเสธการสั่งทั้งหมด; ถ้ามีเมนูรายการใดในคำขอที่มีสถานะ "ปิดชั่วคราว" อยู่ ณ ขณะยืนยัน -> ปฏิเสธการสั่ง และต้องระบุให้ลูกค้าทราบว่ารายการใดสั่งไม่ได้

**อ้างอิง:** [[../../01-requirements/01-spec/20260802-001-table-qr-ordering|20260802-001]] และ [[../01-prototypes/20260802-001-table-qr-ordering-journey|journey]] steps 4-6

#### ดูคิวออเดอร์สำหรับบาริสต้า

- **คำอธิบาย:** บาริสต้าดึงรายการออเดอร์ที่เข้าคิวเพื่อทำ เรียงตามลำดับที่เข้ามา
- **ผู้เรียกใช้ (Actor):** บาริสต้า
- **เงื่อนไขก่อนทำงาน (Precondition):** ไม่มี (นอกเหนือจากการผ่านการตรวจสอบความยินยอม PDPA แล้ว)

**ข้อมูลนำเข้า (Input):**

| Field | ชนิดข้อมูลเชิงแนวคิด | บังคับ/ไม่บังคับ | คำอธิบาย |
|---|---|---|---|
| ตัวกรองสถานะ | ค่าเลือกจากรายการ | ไม่บังคับ | ตัวกรองแสดงเฉพาะออเดอร์ในสถานะที่ต้องการ (ไม่ได้ระบุรายละเอียดใน spec ปัจจุบัน) |

**ผลลัพธ์ (Output):**

| Field | ชนิดข้อมูลเชิงแนวคิด | คำอธิบาย |
|---|---|---|
| รายการออเดอร์ในคิว[] | รายการของ | ออเดอร์ที่รอดำเนินการ พร้อมรหัสออเดอร์, โต๊ะที่สั่ง, รายการสินค้าในออเดอร์, สถานะปัจจุบัน, เวลาที่สั่ง |

**กฎธุรกิจ/การตรวจสอบ (Business Rules):** ต้องรองรับการทำงานต่อได้ชั่วคราวแม้เครือข่ายขัดข้อง โดยใช้ข้อมูลคิวที่โหลดไว้แล้ว (offline-first บางส่วน) แล้ว sync ข้อมูลกลับเมื่อเครือข่ายกลับมา โดยใช้กติกาเชิงแนวคิด "ข้อมูลที่ซิงก์เข้าระบบล่าสุดเป็นค่าที่ถูกต้อง" หากพบข้อมูลสถานะเดียวกันขัดแย้งกันจากหลายอุปกรณ์ (ตามหลักการที่ 3 ใน [[high-level-architecture|high-level-architecture.md]] หัวข้อ 7)

**กรณีผิดพลาดเชิงธุรกิจ (Business Exceptions):** ไม่มี (เป็น query operation)

**อ้างอิง:** [[../../01-requirements/01-spec/20260802-001-table-qr-ordering|20260802-001]] และ [[../01-prototypes/20260802-001-table-qr-ordering-journey|journey]] step 5

#### เปลี่ยนสถานะออเดอร์

- **คำอธิบาย:** บาริสต้าปรับสถานะออเดอร์เป็น "กำลังทำ" หรือ "เสร็จแล้ว" หลังจากทำเครื่องดื่ม/อาหาร หรือพนักงานเสิร์ฟปรับสถานะเป็น "เสิร์ฟแล้ว" หลังจากนำไปเสิร์ฟที่โต๊ะจริงแล้ว เมื่อบาริสต้ากดยืนยันว่าออเดอร์ "เสร็จแล้ว" ระบบต้องแจ้งเตือนพนักงานเสิร์ฟโดยอัตโนมัติทันที
- **ผู้เรียกใช้ (Actor):** บาริสต้า (เปลี่ยนเป็น "กำลังทำ"/"เสร็จแล้ว"), พนักงานเสิร์ฟ (เปลี่ยนเป็น "เสิร์ฟแล้ว")
- **เงื่อนไขก่อนทำงาน (Precondition):** ออเดอร์ต้องมีอยู่จริง และสถานะปัจจุบันต้องเป็นสถานะก่อนหน้าสถานะใหม่ที่ต้องการเปลี่ยนไปตามลำดับที่กำหนด

**ข้อมูลนำเข้า (Input):**

| Field | ชนิดข้อมูลเชิงแนวคิด | บังคับ/ไม่บังคับ | คำอธิบาย |
|---|---|---|---|
| รหัสออเดอร์ | ข้อความ (อ้างอิงออเดอร์) | บังคับ | ออเดอร์ที่ต้องการเปลี่ยนสถานะ |
| สถานะใหม่ | ค่าเลือกจากรายการ (กำลังทำ / เสร็จแล้ว / เสิร์ฟแล้ว) | บังคับ | สถานะที่ต้องการเปลี่ยนไป |

**ผลลัพธ์ (Output):**

| Field | ชนิดข้อมูลเชิงแนวคิด | คำอธิบาย |
|---|---|---|
| รหัสออเดอร์ | ข้อความ | ออเดอร์ที่ถูกเปลี่ยนสถานะ |
| สถานะใหม่ | ค่าเลือกจากรายการ | สถานะล่าสุดของออเดอร์ |
| เวลาที่เปลี่ยนสถานะ | วันที่/เวลา | เวลาที่การเปลี่ยนสถานะสำเร็จ |

**กฎธุรกิจ/การตรวจสอบ (Business Rules):** สถานะต้องไหลตามลำดับ "รับออเดอร์แล้ว -> กำลังทำ -> เสร็จแล้ว -> เสิร์ฟแล้ว" เท่านั้น ห้ามข้ามลำดับหรือย้อนกลับ; เมื่อเปลี่ยนเป็น "เสร็จแล้ว" ต้องกระตุ้นการแจ้งเตือนพนักงานเสิร์ฟอัตโนมัติทันที; ทุกการเปลี่ยนสถานะต้องกระตุ้นบันทึกเหตุการณ์ประเภท "เปลี่ยนสถานะออเดอร์" พร้อมผู้ทำรายการ; ต้องทำงานแบบทันที (synchronous เชิงแนวคิด) เพราะสถานะที่ลูกค้าเห็นและการแจ้งเตือนพนักงานเสิร์ฟต้องเกิดต่อเนื่องจากการกดยืนยันทันที

**กรณีผิดพลาดเชิงธุรกิจ (Business Exceptions):** ถ้าสถานะใหม่ที่ขอไม่ใช่สถานะถัดไปตามลำดับที่กำหนด -> ปฏิเสธการเปลี่ยนสถานะ; ถ้าออเดอร์ไม่มีอยู่จริง -> ปฏิเสธ

**อ้างอิง:** [[../../01-requirements/01-spec/20260802-001-table-qr-ordering|20260802-001]], [[../../01-requirements/01-spec/20260802-003-audit-log|20260802-003]] และ [[../01-prototypes/20260802-001-table-qr-ordering-journey|journey]] steps 6-11

#### ติดตามสถานะออเดอร์แบบต่อเนื่อง (Subscription เชิงแนวคิด)

- **คำอธิบาย:** เป็น operation แบบสมัครรับข้อมูลต่อเนื่อง (subscription เชิงแนวคิด) — ลูกค้าเรียก operation นี้ครั้งเดียวจากหน้าจอสั่งอาหาร แล้วรับผลลัพธ์สถานะออเดอร์ใหม่ทุกครั้งที่มีการเปลี่ยนแปลง (รับออเดอร์แล้ว/กำลังทำ/เสร็จแล้ว/เสิร์ฟแล้ว) ต่อเนื่องจนกว่าจะยกเลิกการสมัครรับข้อมูลหรือปิดหน้าจอ ไม่ใช่การเรียกแบบร้องขอ-ตอบครั้งเดียวจบ (ไม่ระบุกลไกทางเทคนิคเฉพาะเจาะจงของการส่งข้อมูลต่อเนื่องนี้)
- **ผู้เรียกใช้ (Actor):** ลูกค้า
- **เงื่อนไขก่อนทำงาน (Precondition):** ออเดอร์ที่ติดตามต้องมีอยู่จริงและเป็นของโต๊ะที่กำลังเปิดหน้าสั่งอาหารอยู่

**ข้อมูลนำเข้า (Input):**

| Field | ชนิดข้อมูลเชิงแนวคิด | บังคับ/ไม่บังคับ | คำอธิบาย |
|---|---|---|---|
| รหัสออเดอร์ | ข้อความ (อ้างอิงออเดอร์) | บังคับ | ออเดอร์ที่ต้องการติดตามสถานะ |

**ผลลัพธ์ (Output):**

| Field | ชนิดข้อมูลเชิงแนวคิด | คำอธิบาย |
|---|---|---|
| สถานะออเดอร์ปัจจุบัน | ค่าเลือกจากรายการ | ส่งกลับทุกครั้งที่มีการเปลี่ยนแปลงสถานะ |
| เวลาที่เปลี่ยนสถานะล่าสุด | วันที่/เวลา | เวลาที่สถานะปัจจุบันถูกบันทึก |

**กฎธุรกิจ/การตรวจสอบ (Business Rules):** ต้องส่งผลลัพธ์สถานะใหม่ทุกครั้งที่มีการเปลี่ยนแปลงจนกว่าลูกค้าจะยกเลิกการสมัครรับข้อมูล/ปิดหน้าจอ ตามที่ requirement 20260802-001 กำหนดให้ลูกค้าเห็นสถานะแบบ real-time ตลอดเวลา

**กรณีผิดพลาดเชิงธุรกิจ (Business Exceptions):** ถ้ารหัสออเดอร์ที่ระบุไม่มีอยู่จริง -> ปฏิเสธการสมัครรับข้อมูล

**อ้างอิง:** [[../../01-requirements/01-spec/20260802-001-table-qr-ordering|20260802-001]] และ [[../01-prototypes/20260802-001-table-qr-ordering-journey|journey]] steps 6, 7, 9, 11

#### ดูสรุปยอดขายตามช่วงเวลา (preset)

- **คำอธิบาย:** ผู้บริหารร้านเลือกช่วงเวลา preset (วันนี้/สัปดาห์นี้/เดือนนี้) เพื่อดูยอดขายรวมและจำนวนออเดอร์ที่เกิดขึ้นในช่วงเวลานั้น
- **ผู้เรียกใช้ (Actor):** ผู้บริหารร้าน
- **เงื่อนไขก่อนทำงาน (Precondition):** ผู้เรียกใช้ต้องมีบทบาทผู้บริหารร้าน (ผ่าน operation "ตรวจสอบสิทธิ์การเข้าถึงตามบทบาท")

**ข้อมูลนำเข้า (Input):**

| Field | ชนิดข้อมูลเชิงแนวคิด | บังคับ/ไม่บังคับ | คำอธิบาย |
|---|---|---|---|
| ช่วงเวลาที่เลือก | ค่าเลือกจากรายการ (วันนี้ / สัปดาห์นี้ / เดือนนี้) | บังคับ | preset ช่วงเวลาที่ต้องการดูข้อมูล |

**ผลลัพธ์ (Output):**

| Field | ชนิดข้อมูลเชิงแนวคิด | คำอธิบาย |
|---|---|---|
| ยอดขายรวม | จำนวนเงิน | ยอดขายรวมของออเดอร์ในช่วงเวลาที่เลือก |
| จำนวนออเดอร์ | ตัวเลข | จำนวนออเดอร์ในช่วงเวลาที่เลือก |
| ช่วงเวลาที่ใช้คำนวณ | ค่าเลือกจากรายการ | ยืนยัน preset ที่ใช้คำนวณผลลัพธ์นี้ |

**กฎธุรกิจ/การตรวจสอบ (Business Rules):** คำนวณจากออเดอร์ที่มี "เวลาที่สั่ง" อยู่ในช่วงที่เลือกเท่านั้น; ใช้ "ราคา ณ ขณะสั่ง" ของรายการสินค้าในออเดอร์แต่ละรายการในการคำนวณยอดขายรวม (ไม่ใช้ราคาปัจจุบันของเมนู); จำกัดเฉพาะ preset ที่กำหนดไว้ล่วงหน้า ไม่รองรับช่วงเวลาแบบกำหนดเอง; ต้องกระตุ้นบันทึกเหตุการณ์ประเภท "เข้าถึง sales dashboard"

**กรณีผิดพลาดเชิงธุรกิจ (Business Exceptions):** ถ้าผู้เรียกไม่ใช่บทบาทผู้บริหารร้าน -> ปฏิเสธการเข้าถึงทั้งหมด ไม่แสดงข้อมูลใด ๆ

**อ้างอิง:** [[../../01-requirements/01-spec/20260802-002-sales-dashboard|20260802-002]] และ [[../01-prototypes/20260802-002-sales-dashboard-journey|journey]]

### 2.2 รายการสินค้าในออเดอร์

### 2.5 ผู้ใช้/พนักงาน

#### ตรวจสอบสิทธิ์การเข้าถึงตามบทบาท

- **คำอธิบาย:** ตรวจสอบว่าผู้เรียกใช้มีบทบาทที่ได้รับอนุญาตสำหรับ operation ที่ต้องการเรียกหรือไม่ ก่อนอนุญาตให้ทำงานต่อ ใช้ร่วมกันเป็นเงื่อนไขก่อนทำงานของ operation "ดูสรุปยอดขายตามช่วงเวลา" และ "ดู Audit Log ย้อนหลัง" ที่จำกัดสิทธิ์เฉพาะบทบาทผู้บริหารร้าน
- **ผู้เรียกใช้ (Actor):** ผู้บริหารร้าน (เป็นผู้เรียกใช้งานปลายทาง — operation นี้ถูกเรียกใช้งานภายในโดย operation อื่นเป็นเงื่อนไขก่อนทำงานเสมอ ไม่ใช่ operation ที่เรียกเดี่ยว ๆ)
- **เงื่อนไขก่อนทำงาน (Precondition):** ผู้เรียกใช้ต้องมีบัญชีผู้ใช้ในระบบแล้ว

**ข้อมูลนำเข้า (Input):**

| Field | ชนิดข้อมูลเชิงแนวคิด | บังคับ/ไม่บังคับ | คำอธิบาย |
|---|---|---|---|
| บทบาทของผู้เรียกใช้ | ค่าเลือกจากรายการ (พนักงานเสิร์ฟ / บาริสต้า / ผู้บริหารร้าน) | บังคับ | บทบาทของผู้เรียกใช้ที่ต้องตรวจสอบ |
| operation/ทรัพยากรที่ต้องการเข้าถึง | ข้อความ | บังคับ | ระบุว่ากำลังตรวจสอบสิทธิ์เข้าถึง operation ใด |

**ผลลัพธ์ (Output):**

| Field | ชนิดข้อมูลเชิงแนวคิด | คำอธิบาย |
|---|---|---|
| ผลการตรวจสอบ | ค่าจริง/เท็จ (อนุญาต / ปฏิเสธ) | ผลว่าอนุญาตให้เข้าถึงหรือไม่ |

**กฎธุรกิจ/การตรวจสอบ (Business Rules):** เฉพาะบทบาท "ผู้บริหารร้าน" เท่านั้นที่ผ่านการตรวจสอบสำหรับหน้า sales dashboard และหน้า audit log บทบาทอื่น (พนักงานเสิร์ฟ, บาริสต้า) ต้องถูกปฏิเสธเสมอ

**กรณีผิดพลาดเชิงธุรกิจ (Business Exceptions):** ถ้าบทบาทไม่ตรงตามที่กำหนด -> ปฏิเสธการเข้าถึงทันที

**อ้างอิง:** [[../../01-requirements/01-spec/20260802-002-sales-dashboard|20260802-002]], [[../../01-requirements/01-spec/20260802-003-audit-log|20260802-003]], [[../01-prototypes/20260802-002-sales-dashboard-journey|journey002]] steps 1-3 และ [[../01-prototypes/20260802-003-audit-log-journey|journey003]] steps 6-9

> หมายเหตุ: spec ปัจจุบันไม่มีรายละเอียด operation สำหรับการสร้าง/จัดการบัญชีผู้ใช้พนักงาน (add/edit บัญชี, กำหนดบทบาท) หรือ operation ยืนยันตัวตนพนักงาน (authentication) จึงไม่ได้ระบุ operation เหล่านี้ในเอกสารนี้ — ดูหัวข้อ 5

### 2.6 บันทึกเหตุการณ์ (Audit Log Record)

#### บันทึกเหตุการณ์ (Audit Logging)

- **คำอธิบาย:** ดักจับเหตุการณ์สำคัญที่เกิดขึ้นจาก operation อื่น (สร้างออเดอร์ใหม่, เปลี่ยนสถานะออเดอร์, เปิดเมนู, ปิดเมนู, เข้าถึง sales dashboard) แล้วบันทึกเป็นบันทึกเหตุการณ์ 1 รายการ operation นี้ถูกเรียกใช้งานภายในโดยอัตโนมัติทุกครั้งที่เกิดเหตุการณ์ที่กำหนด ไม่ใช่ operation ที่ผู้ใช้เรียกตรง
- **ผู้เรียกใช้ (Actor):** ระบบ (เรียกใช้งานภายในอัตโนมัติจาก operation ต้นทางเหตุการณ์ ไม่มีผู้ใช้เรียกตรง)
- **เงื่อนไขก่อนทำงาน (Precondition):** ต้องมีเหตุการณ์ประเภทที่กำหนดไว้เกิดขึ้นจริง (สร้างออเดอร์ใหม่ / เปลี่ยนสถานะออเดอร์ / เปิดเมนู / ปิดเมนู / เข้าถึง sales dashboard)

**ข้อมูลนำเข้า (Input):**

| Field | ชนิดข้อมูลเชิงแนวคิด | บังคับ/ไม่บังคับ | คำอธิบาย |
|---|---|---|---|
| เวลาที่เกิดเหตุการณ์ | วันที่/เวลา | บังคับ | timestamp ของเหตุการณ์ |
| ผู้ทำรายการ | ข้อความ (อ้างอิงผู้ใช้/พนักงาน) | บังคับ | บัญชีผู้ใช้ที่เป็นผู้ทำรายการ |
| ประเภทเหตุการณ์ | ค่าเลือกจากรายการ (สร้างออเดอร์ใหม่ / เปลี่ยนสถานะออเดอร์ / เปิดเมนู / ปิดเมนู / เข้าถึง sales dashboard) | บังคับ | หมวดของเหตุการณ์ |
| รายละเอียด | ข้อความ | บังคับ | ข้อมูลประกอบเหตุการณ์ (เช่น รหัสออเดอร์ที่เกี่ยวข้อง, เมนูที่ถูกปิด) |

**ผลลัพธ์ (Output):**

| Field | ชนิดข้อมูลเชิงแนวคิด | คำอธิบาย |
|---|---|---|
| รหัส log record | ข้อความ (รหัสอ้างอิง) | ตัวระบุเฉพาะของ log record ที่สร้างขึ้น |

**กฎธุรกิจ/การตรวจสอบ (Business Rules):** ทุก log record ต้องมีครบทั้ง timestamp, ผู้ทำรายการ, ประเภทเหตุการณ์, รายละเอียด ห้ามขาดฟิลด์ใดฟิลด์หนึ่ง; ครอบคลุมเฉพาะ application-level business event เท่านั้น ไม่รวม infrastructure/server log

**กรณีผิดพลาดเชิงธุรกิจ (Business Exceptions):** ไม่มี (เป็น operation ภายในที่ต้องสำเร็จเสมอเมื่อเหตุการณ์ต้นทางเกิดขึ้น)

**อ้างอิง:** [[../../01-requirements/01-spec/20260802-003-audit-log|20260802-003]] และ [[../01-prototypes/20260802-003-audit-log-journey|journey]] steps 1-2

#### ลบบันทึกเหตุการณ์ที่เกินอายุเก็บรักษาอัตโนมัติ

- **คำอธิบาย:** ระบบตรวจสอบอายุของบันทึกเหตุการณ์แต่ละรายการ และลบรายการที่มีอายุเกิน 90 วันออกจากระบบโดยอัตโนมัติ โดยไม่ต้องมีผู้ใช้เรียกใช้งาน
- **ผู้เรียกใช้ (Actor):** ระบบ (ทำงานอัตโนมัติตามรอบเวลา ไม่มีผู้ใช้เรียกตรง)
- **เงื่อนไขก่อนทำงาน (Precondition):** บันทึกเหตุการณ์นั้นมีอายุเกิน 90 วัน นับจาก "เวลาที่เกิดเหตุการณ์"

**ข้อมูลนำเข้า (Input):**

ไม่มี (ทำงานอัตโนมัติตามเงื่อนไขอายุของข้อมูล ไม่รับ input จากผู้เรียก)

**ผลลัพธ์ (Output):**

| Field | ชนิดข้อมูลเชิงแนวคิด | คำอธิบาย |
|---|---|---|
| รายการรหัส log record ที่ถูกลบ[] | รายการของ | รหัส log record ทั้งหมดที่ถูกลบในรอบนี้ |

**กฎธุรกิจ/การตรวจสอบ (Business Rules):** ต้องลบอัตโนมัติตามหลัก data minimization เมื่ออายุเกิน 90 วัน ไม่มีการ export ก่อนลบในเฟสนี้

**กรณีผิดพลาดเชิงธุรกิจ (Business Exceptions):** ไม่มี

**อ้างอิง:** [[../../01-requirements/01-spec/20260802-003-audit-log|20260802-003]] และ [[../01-prototypes/20260802-003-audit-log-journey|journey]] steps 3-5

### 2.7 ความยินยอม (Consent Record)

#### ขอความยินยอม PDPA ตอน onboarding

- **คำอธิบาย:** แสดงเนื้อหายินยอมแบบง่าย (ข้อมูลที่เก็บ+วัตถุประสงค์) ให้พนักงานที่เข้าระบบครั้งแรก แล้วรับผลการกดยืนยัน/ไม่ยินยอม บันทึกผลพร้อม timestamp แบบถาวร
- **ผู้เรียกใช้ (Actor):** พนักงาน (พนักงานเสิร์ฟ/บาริสต้า/ผู้บริหารร้าน) ที่เข้าระบบครั้งแรก
- **เงื่อนไขก่อนทำงาน (Precondition):** พนักงานยังไม่มีบันทึกความยินยอมมาก่อน (ยังไม่เคยผ่านขั้นตอนนี้)

**ข้อมูลนำเข้า (Input):**

| Field | ชนิดข้อมูลเชิงแนวคิด | บังคับ/ไม่บังคับ | คำอธิบาย |
|---|---|---|---|
| ผลการยืนยัน | ค่าจริง/เท็จ (ยินยอม / ไม่ยินยอม) | บังคับ | ผลการกดยืนยัน/ติ๊กยอมรับของพนักงาน |

**ผลลัพธ์ (Output):**

| Field | ชนิดข้อมูลเชิงแนวคิด | คำอธิบาย |
|---|---|---|
| สถานะยินยอม | ค่าจริง/เท็จ | ผลลัพธ์ที่บันทึกไว้ |
| เวลาที่ยินยอม | วันที่/เวลา | timestamp ของการกดยืนยัน |

**กฎธุรกิจ/การตรวจสอบ (Business Rules):** ขอความยินยอมเพียงครั้งเดียวตอน onboarding ไม่ต้องขอซ้ำทุกครั้งที่ login; บันทึกสถานะแบบถาวร ไม่ผูกกับนโยบาย retention 90 วันของ audit log; ถ้าผลคือ "ไม่ยินยอม" ต้องบล็อกการใช้งานระบบทั้งหมดของพนักงานคนนั้นทันที

**กรณีผิดพลาดเชิงธุรกิจ (Business Exceptions):** ถ้าพนักงานเคยยินยอมแล้ว (มี consent record อยู่แล้ว) -> ไม่ต้องแสดงขั้นตอนนี้ซ้ำ

**อ้างอิง:** [[../../01-requirements/01-spec/20260802-004-pdpa-consent|20260802-004]] และ [[../01-prototypes/20260802-004-pdpa-consent-journey|journey]] steps 1-5

#### ตรวจสอบสถานะยินยอมก่อนอนุญาตใช้งาน (Consent Gate)

- **คำอธิบาย:** ตรวจสอบว่าพนักงานที่กำลังจะใช้งานองค์ประกอบใดในระบบมีสถานะยินยอม PDPA เป็น "ยินยอม" แล้วหรือไม่ ก่อนอนุญาตให้เข้าถึงฟังก์ชันตามบทบาท
- **ผู้เรียกใช้ (Actor):** ระบบ (เรียกใช้งานภายในทุกครั้งก่อนพนักงานเข้าถึงองค์ประกอบอื่นใด)
- **เงื่อนไขก่อนทำงาน (Precondition):** ผู้เรียกใช้ต้องเป็นพนักงานที่มีบัญชีผู้ใช้ในระบบ

**ข้อมูลนำเข้า (Input):**

| Field | ชนิดข้อมูลเชิงแนวคิด | บังคับ/ไม่บังคับ | คำอธิบาย |
|---|---|---|---|
| รหัสผู้ใช้/พนักงาน | ข้อความ (อ้างอิงผู้ใช้/พนักงาน) | บังคับ | พนักงานที่กำลังตรวจสอบสถานะยินยอม |

**ผลลัพธ์ (Output):**

| Field | ชนิดข้อมูลเชิงแนวคิด | คำอธิบาย |
|---|---|---|
| ผลการตรวจสอบ | ค่าเลือกจากรายการ (ผ่าน / ถูกบล็อก) | ผลว่าอนุญาตให้ใช้งานต่อได้หรือไม่ |

**กฎธุรกิจ/การตรวจสอบ (Business Rules):** พนักงานที่มีสถานะยินยอมเป็น "ไม่ยินยอม" หรือยังไม่มี consent record ต้องถูกบล็อกจากการใช้งานองค์ประกอบอื่นใดในระบบทั้งหมด (mandatory gate)

**กรณีผิดพลาดเชิงธุรกิจ (Business Exceptions):** ถ้าไม่พบ consent record หรือสถานะเป็น "ไม่ยินยอม" -> บล็อกการใช้งานทั้งหมด

**อ้างอิง:** [[../../01-requirements/01-spec/20260802-004-pdpa-consent|20260802-004]] และ [[../01-prototypes/20260802-004-pdpa-consent-journey|journey]] steps 3-4

## 3. เอนทิตีข้อมูลที่เกี่ยวข้อง

operation ทั้งหมดในเอกสารนี้อ้างอิงเอนทิตีที่นิยามไว้แล้วใน [[database-schema|database-schema.md]] ได้แก่ ออเดอร์ (3.1), รายการสินค้าในออเดอร์ (3.2), โต๊ะ (3.3), เมนู (3.4), ผู้ใช้/พนักงาน (3.5), บันทึกเหตุการณ์ (3.6) และความยินยอม (3.7) — ไม่มีการนิยาม attribute ซ้ำในเอกสารนี้ Input/Output ของแต่ละ operation ข้างต้นใช้ชื่อ field ที่สอดคล้องกับชื่อ attribute ใน database-schema.md โดยตรง หากต้องการดูชนิดข้อมูล ข้อจำกัดเชิงธุรกิจ และความสัมพันธ์ระหว่างเอนทิตีแบบเต็ม ให้ดูที่เอกสารนั้น

## 4. หลักการเชิงแนวคิดของ Operation (Conceptual Principles)

- operation "สั่งออเดอร์ (สร้างออเดอร์ใหม่)" ต้อง idempotent เชิงแนวคิด — การเรียกซ้ำด้วยคำขอเดิม (กำกับด้วยค่าระบุคำขอซ้ำเชิงแนวคิด) ต้องไม่สร้างออเดอร์ซ้ำ (ยืนยันจาก user)
- operation "ติดตามสถานะออเดอร์แบบต่อเนื่อง" ต้องเป็นรูปแบบ "สมัครรับข้อมูลต่อเนื่อง" (subscription) เชิงแนวคิด — เรียกครั้งเดียวแล้วรับผลลัพธ์ใหม่ทุกครั้งที่มีการเปลี่ยนแปลงจนกว่าจะยกเลิก/ปิดหน้าจอ ไม่ใช่การเรียกแบบร้องขอ-ตอบครั้งเดียวจบ (ยืนยันจาก user; ไม่ระบุกลไกทางเทคนิคของการส่งข้อมูลต่อเนื่อง)
- operation "เปลี่ยนสถานะออเดอร์" ต้องทำงานแบบทันที (synchronous เชิงแนวคิด) เพราะการแจ้งเตือนพนักงานเสิร์ฟและสถานะที่ลูกค้าเห็นต้องเกิดต่อเนื่องจากการกดยืนยันทันที ไม่รอประมวลผลแบบ async
- operation ที่ทำงานโดยระบบเองอัตโนมัติ (บันทึกเหตุการณ์, ลบบันทึกเหตุการณ์ที่เกินอายุ, ตรวจสอบสถานะยินยอมก่อนอนุญาตใช้งาน) ไม่มีผู้ใช้ที่เป็นบุคคลเรียกใช้งานตรง แต่ถูกกระตุ้นจาก operation อื่นหรือทำงานตามเงื่อนไข/รอบเวลาที่กำหนดไว้เชิงแนวคิด
- operation "ดูคิวออเดอร์สำหรับบาริสต้า" และ "เปลี่ยนสถานะออเดอร์" (ฝั่งบาริสต้า) ต้องรองรับ offline-first บางส่วน — ทำงานต่อได้ชั่วคราวด้วยข้อมูลที่โหลดไว้แล้วแม้เครือข่ายขัดข้อง แล้ว sync กลับด้วยกติกา "ข้อมูลที่ซิงก์เข้าระบบล่าสุดเป็นค่าที่ถูกต้อง" เมื่อเครือข่ายกลับมา (ตามหลักการที่ 3 ใน [[high-level-architecture|high-level-architecture.md]] หัวข้อ 7)

## 5. ประเด็นที่ยังไม่ชัดเจน / รอการตัดสินใจ (Open Questions)

- ยังไม่มี operation สำหรับสร้าง/จัดการบัญชีผู้ใช้พนักงาน (add/edit บัญชี, กำหนด/เปลี่ยนบทบาท) เนื่องจาก spec ปัจจุบัน (20260802-001 ถึง 20260802-004) ไม่ได้ระบุรายละเอียดขั้นตอนนี้ไว้ — ต้องรอ requirement เพิ่มเติมก่อนจึงจะออกแบบ operation นี้ได้
- operation "ยืนยันตัวตนพนักงานก่อนเข้าใช้งานระบบ" (login/authentication เชิงแนวคิด) ยังไม่มีรายละเอียดใน spec ปัจจุบันว่าใช้ข้อมูลอะไรยืนยันตัวตน spec เพียงระบุว่าพนักงานมีบัญชีผู้ใช้และบทบาท จึงยังไม่สามารถออกแบบ operation นี้แบบเต็มรูปแบบได้ในเอกสารนี้
- operation "ดู Audit Log ย้อนหลัง" ยังไม่มีรายละเอียดตัวกรอง (เช่น filter ตามช่วงเวลา/ประเภทเหตุการณ์/ผู้ทำรายการ) ใน spec 20260802-003 ปัจจุบัน จึงยังไม่มี field ตัวกรองใน Input ของ operation นี้
- operation "ดูคิวออเดอร์สำหรับบาริสต้า" ยังไม่มีรายละเอียดตัวกรองสถานะที่ชัดเจนจาก spec ปัจจุบัน (ระบุไว้เป็น "ไม่บังคับ" ในตาราง Input เพื่อรอความชัดเจนเพิ่มเติม)
