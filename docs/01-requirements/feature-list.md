## รายละเอียดฟีเจอร์

### 20260802-001 — ระบบสั่งกาแฟจากโต๊ะด้วยการสแกน QR Code (`Must have`)

ลูกค้าสแกน QR code ประจำโต๊ะเพื่อสั่งเมนู ออเดอร์เข้าคิวบาริสต้าโดยตรง เมื่อทำเสร็จระบบแจ้งเตือนพนักงานเสิร์ฟอัตโนมัติ พร้อมแสดงสถานะออเดอร์แบบ real-time ให้ลูกค้าเห็น และผู้จัดการร้าน/บาริสต้าปิด-เปิดเมนูชั่วคราวได้

**เหตุผลจัดลำดับ:** เป็น core business flow ของทั้งระบบ — ร้านใช้งานระบบไม่ได้เลยถ้าไม่มีฟีเจอร์นี้ (จัดตามเกณฑ์ default: flow หลักที่ระบบใช้งานไม่ได้เลยถ้าขาด)

**เอกสารต้นทาง:** [[01-spec/20260802-001-table-qr-ordering.md|20260802-001-table-qr-ordering.md]]

### 20260823-005 — การจัดการบัญชีพนักงานและการยืนยันตัวตน (`Must have`)

ผู้บริหารร้าน (เจ้าของร้าน/ผู้จัดการร้าน) เป็นบทบาทเดียวที่สร้าง/แก้ไข/ปลด (offboard) บัญชีพนักงานได้ พนักงานยืนยันตัวตนด้วย PIN code ต่อเครื่อง/อุปกรณ์แทน username+password ระบบต้องรู้ session ว่าใครยืนยันตัวตนอยู่ ณ ขณะนั้น เพื่อระบุ "ผู้ทำรายการ" และตรวจสอบสิทธิ์ตามบทบาท (RBAC) และการปลดพนักงานออกจากระบบเป็น trigger เริ่มนับ 90 วันสำหรับ anonymize ข้อมูลระบุตัวตนใน audit log/consent record

**เหตุผลจัดลำดับ:** จัดเป็น **Must have** ตามการยืนยันของ user แม้เนื้อหาเป็นเชิง backend/infrastructure ไม่ใช่ user-facing flow โดยตรงเหมือน 20260802-001 แต่เป็น technical prerequisite ที่บล็อกการ implement จริงของ 20260802-002 (Should have), 20260802-003 (Should have) และ 20260802-004 (Could have) แทบทั้งหมด — ทั้ง 3 spec สมมติไว้ล่วงหน้าว่ามีบัญชี/บทบาท/การยืนยันตัวตนอยู่แล้วโดยไม่ได้ระบุรายละเอียด จึงต้องมีบัญชี+การยืนยันตัวตนใช้งานได้จริงก่อน จึงจะมี audit log ที่ระบุ actor ได้ถูกต้อง, RBAC ที่บังคับใช้ได้จริง, และ consent gate ที่ผูกกับบัญชีจริงได้ (การตัดสินใจของ user ไม่ใช่การใช้เกณฑ์ default)

**เอกสารต้นทาง:** [[01-spec/20260823-005-staff-account-and-authentication.md|20260823-005-staff-account-and-authentication.md]]

### 20260802-002 — หน้า Dashboard ดูยอดขาย (`Should have`)

เจ้าของร้าน/แอดมินดูยอดขายรวมและจำนวนออเดอร์ตามช่วงเวลา preset ("วันนี้", "สัปดาห์นี้", "เดือนนี้")

**เหตุผลจัดลำดับ:** spec ระบุไว้เองในหมายเหตุว่าเป็น "Medium priority ... มีประโยชน์แต่ไม่ใช่ core flow ที่บล็อกการใช้งานร้าน" จึงจัดเป็น Should have — สำคัญรองจาก flow การสั่งกาแฟหลัก แต่ร้านยังเปิดขายได้ถ้ายังไม่มีฟีเจอร์นี้

**เอกสารต้นทาง:** [[01-spec/20260802-002-sales-dashboard.md|20260802-002-sales-dashboard.md]]

### 20260802-003 — ระบบบันทึก Log (Audit Trail) (`Should have`)

บันทึก log เหตุการณ์สำคัญ (สร้าง/เปลี่ยนสถานะออเดอร์, เปิด-ปิดเมนู, การเข้าถึง dashboard) พร้อม timestamp และผู้ทำรายการ เก็บไว้ 90 วันแล้วลบอัตโนมัติ จำกัดสิทธิ์ดูเฉพาะผู้จัดการร้าน/แอดมิน นอกจากนี้ยังมี business rule เพิ่มเติม (2026-08-23) ให้ anonymize ข้อมูลระบุตัวตนของผู้ทำรายการในทุก log record หลังพนักงานคนนั้นถูกปลดออกจากระบบ (offboard) ครบ 90 วัน โดยไม่ลบ log record ทิ้ง

**เหตุผลจัดลำดับ:** spec ระบุไว้เองในหมายเหตุว่าเป็น "Medium priority ... supporting feature เพื่อความโปร่งใส/ตรวจสอบได้ ไม่ใช่ core flow" จึงจัดเป็น Should have ส่วน business rule การ anonymize ที่เพิ่มเข้ามาวันนี้เป็นรายละเอียดเสริมของฟีเจอร์เดิม ไม่กระทบการจัดลำดับ MoSCoW เดิม

**เอกสารต้นทาง:** [[01-spec/20260802-003-audit-log.md|20260802-003-audit-log.md]]

### 20260802-004 — ขอความยินยอม (Consent) ตาม PDPA จากพนักงาน (`Could have`)

พนักงานทุกคนต้องกดยินยอมครั้งเดียวตอน onboarding ก่อนใช้งานระบบได้ ระบบบันทึกสถานะยินยอมพร้อม timestamp แบบถาวร นอกจากนี้ยังมี business rule เพิ่มเติม (2026-08-23) ให้ anonymize ข้อมูลระบุตัวตนใน consent record หลังพนักงานคนนั้นถูกปลดออกจากระบบ (offboard) ครบ 90 วัน โดยสถานะยินยอม+timestamp ยังคงเก็บไว้ถาวรตามเดิม

**เหตุผลจัดลำดับ:** แม้ spec จะระบุว่าเป็นเงื่อนไข mandatory gate ที่บล็อกการใช้งานระบบทั้งหมดหากไม่ยินยอม (ซึ่งเข้าเกณฑ์ Must have ได้เช่นกัน) แต่ผู้ใช้ยืนยันให้จัดเป็น **Could have** เนื่องจากธุรกิจขนาดเล็กแบบร้านกาแฟนี้ยังไม่มีการบังคับใช้ PDPA อย่างเข้มงวด จึงมองว่าเป็นส่วนเสริมที่ทำทีหลังได้โดยไม่กระทบการเปิดร้าน (เป็นการตัดสินใจของ user ไม่ใช่การใช้เกณฑ์ default) ส่วน business rule การ anonymize ที่เพิ่มเข้ามาวันนี้เป็นรายละเอียดเสริมของฟีเจอร์เดิม ไม่กระทบการจัดลำดับ MoSCoW เดิม

**เอกสารต้นทาง:** [[01-spec/20260802-004-pdpa-consent.md|20260802-004-pdpa-consent.md]]

## ผลการตรวจสอบ (Audit)

ตรวจสอบ `backlog.md` (5 รายการ) เทียบกับไฟล์ใน `01-spec/` ทั้ง 5 ไฟล์ (ไม่รวม `index.md`) แล้ว:

- backlog ทั้ง 5 แถวมีลิงก์ไปยัง spec ที่มีอยู่จริงครบทุกรายการ รวมถึงแถวใหม่ 20260823-005 ที่ลิงก์ไปยัง `20260823-005-staff-account-and-authentication.md` ที่มีอยู่จริง — ไม่พบ broken link
- ไม่พบ spec ไฟล์ใดที่มีอยู่จริงแต่ไม่ถูกอ้างอิงใน backlog (ไม่มี orphan spec)
- สถานะใน backlog ("รอดำเนินการ") สอดคล้องกับสถานะ "ร่าง (Draft)" ในทุก spec ทั้ง 5 ฉบับ รวมถึง 20260802-003 และ 20260802-004 ที่ถูกแก้ไขเพิ่มเนื้อหาวันนี้ (2026-08-23) — เพิ่ม business rule การ anonymize ข้อมูลระบุตัวตนหลัง offboarding 90 วัน แต่ยังคงสถานะ "ร่าง (Draft)" เดิม ไม่มีการเปลี่ยนสถานะที่ทำให้ backlog กับ spec ไม่สอดคล้องกัน
- 20260823-005 ถูกสร้างขึ้นเพื่อปิดช่องว่าง (gap) ที่พบระหว่างการทำ design/testing ว่า spec 20260802-002/003/004 สมมติไว้ล่วงหน้าว่ามีบัญชีพนักงาน/บทบาท/การยืนยันตัวตนอยู่แล้วโดยไม่ได้ระบุรายละเอียด — เอกสารนี้จึงมีลิงก์อ้างอิงไป-กลับกับทั้ง 3 spec ดังกล่าวและ `test-plan.md` หัวข้อ 5.4 ครบถ้วน ไม่พบความไม่สอดคล้อง

สรุป: ไม่พบความไม่สอดคล้องระหว่าง backlog และ spec

(ตรวจสอบซ้ำ (re-audit) เมื่อ 2026-08-23: backlog.md เพิ่มจาก 4 เป็น 5 รายการ — เพิ่ม 20260823-005 "การจัดการบัญชีพนักงานและการยืนยันตัวตน" และมีการแก้ไขเนื้อหา 20260802-003/20260802-004 เพิ่ม business rule การ anonymize ข้อมูลระบุตัวตนหลัง offboarding 90 วัน ทั้งหมดสอดคล้องกันดี ไม่พบปัญหาใหม่)
