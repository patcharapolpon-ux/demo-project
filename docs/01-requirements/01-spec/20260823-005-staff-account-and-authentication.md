## ความต้องการ (Requirement)

ระบบต้องมีกลไกจัดการบัญชีพนักงานและยืนยันตัวตนของพนักงาน (พนักงานเสิร์ฟ, บาริสต้า, ผู้บริหารร้าน) ดังนี้:

**การจัดการบัญชีพนักงาน** — ผู้บริหารร้าน (เจ้าของร้าน/ผู้จัดการร้าน) เป็นบทบาทเดียวในระบบที่มีสิทธิ์สร้าง/แก้ไข/ปลดบัญชีพนักงานคนอื่น (รวมถึงบัญชีผู้บริหารร้านคนอื่นด้วย) บทบาทอื่น (พนักงานเสิร์ฟ, บาริสต้า) ไม่มีสิทธิ์นี้เลย ข้อมูลบัญชีพนักงานที่ต้องเก็บได้แก่ ชื่อ, ข้อมูลบัญชีผู้ใช้ (ต้องไม่ซ้ำกันในระบบ), บทบาท (พนักงานเสิร์ฟ/บาริสต้า/ผู้บริหารร้าน — 1 บัญชีมีได้ 1 บทบาทเท่านั้น) และ PIN code สำหรับยืนยันตัวตน

**การยืนยันตัวตน** — ใช้ PIN code สั้น ๆ ต่อเครื่อง/อุปกรณ์ แทน username+password แบบมาตรฐาน พนักงานเลือกบัญชีของตัวเอง (หรือใส่ข้อมูลระบุบัญชี) แล้วกรอก PIN บนอุปกรณ์ที่ใช้งานประจำจุด (เช่น แท็บเล็ต kiosk mode ของบาริสต้า/พนักงานเสิร์ฟ) เพื่อยืนยันตัวตนก่อนเข้าใช้งานฟังก์ชันตามบทบาทของตน กรณีพนักงานลืม PIN ผู้บริหารร้านเป็นผู้รีเซ็ตให้เองแบบ manual เท่านั้น ไม่มีกลไก self-service ผ่าน email/SMS

**การปลดพนักงานออกจากระบบ (Offboarding)** — เป็น operation ที่แยกออกจาก "แก้ไขข้อมูลบัญชี" เมื่อพนักงานลาออกจริง ผู้บริหารร้านกดปลดบัญชีนี้ ทำให้พนักงานคนนั้น login (ยืนยันตัวตนด้วย PIN) ไม่ได้อีกทันที และเป็นจุดเริ่มต้น (trigger) ของการนับระยะเวลา 90 วันสำหรับ anonymize ข้อมูลระบุตัวตนใน consent record และ audit log ที่อ้างอิงถึงพนักงานคนนี้ ตาม NFR ที่ยืนยันไว้แล้วใน [[../../03-testing/01-test-plan/test-plan|test-plan.md]] หัวข้อ 5.4 (รายละเอียดกลไก anonymize จะถูกเพิ่มในการแก้ไข [[20260802-003-audit-log|20260802-003]]/[[20260802-004-pdpa-consent|20260802-004]] แยกต่างหากในงานถัดไป ไม่ได้ระบุซ้ำในเอกสารนี้)

**Session / การรู้ว่าใคร login อยู่** — ระบบต้องรู้ว่าใครยืนยันตัวตนอยู่ ณ ขณะนั้น (session เชิงแนวคิด) บนอุปกรณ์นั้น เพื่อใช้ระบุ "ผู้ทำรายการ" ใน audit log ([[20260802-003-audit-log|20260802-003]]) และตรวจสอบบทบาทสำหรับ RBAC ของหน้า sales dashboard/audit log ([[20260802-002-sales-dashboard|20260802-002]], [[20260802-003-audit-log|20260802-003]]) ได้ถูกต้อง

## ขอบเขต (Scope)

### สิ่งที่ต้องทำ (In scope)
- Operation สร้างบัญชีพนักงานใหม่ (ชื่อ, ข้อมูลบัญชีผู้ใช้ที่ไม่ซ้ำ, บทบาท 1 ใน 3, PIN code) — จำกัดสิทธิ์เฉพาะผู้บริหารร้าน
- Operation แก้ไขข้อมูลบัญชีพนักงาน (เช่น เปลี่ยนชื่อ, เปลี่ยนบทบาท, รีเซ็ต PIN แบบ manual) — จำกัดสิทธิ์เฉพาะผู้บริหารร้าน
- Operation ปลดพนักงานออกจากระบบ (offboard) แยกจาก operation แก้ไขข้อมูลบัญชี — จำกัดสิทธิ์เฉพาะผู้บริหารร้าน ทำให้บัญชีนั้น login ไม่ได้อีกทันที และเป็น trigger เริ่มนับ retention 90 วันตาม [[../../03-testing/01-test-plan/test-plan|test-plan.md]] หัวข้อ 5.4
- กลไกยืนยันตัวตนด้วย PIN code ต่อเครื่อง/อุปกรณ์ (เลือกบัญชี + กรอก PIN)
- Session เชิงแนวคิดที่ระบุตัวผู้ใช้ที่ยืนยันตัวตนอยู่บนอุปกรณ์นั้น ใช้ประกอบการระบุผู้ทำรายการใน audit log และการตรวจสอบสิทธิ์ตามบทบาท (RBAC)
- การรีเซ็ต PIN แบบ manual โดยผู้บริหารร้าน กรณีพนักงานลืม PIN

### สิ่งที่ไม่ทำ (Out of scope)
- Self-service password/PIN reset ผ่าน email/SMS
- Multi-factor authentication (MFA)
- สิทธิ์/บทบาทเพิ่มเติมนอกเหนือจาก 3 บทบาทเดิม (พนักงานเสิร์ฟ/บาริสต้า/ผู้บริหารร้าน) ที่มีอยู่แล้ว
- บัญชีผู้ใช้สำหรับลูกค้า (ลูกค้าไม่มีบัญชี ตาม [[20260802-001-table-qr-ordering|20260802-001]] และ [[20260802-004-pdpa-consent|20260802-004]] เดิม)
- รายละเอียดกลไก anonymize ข้อมูลระบุตัวตนหลัง offboarding ครบ 90 วัน (จะระบุในการแก้ไข [[20260802-003-audit-log|20260802-003]]/[[20260802-004-pdpa-consent|20260802-004]] แยกต่างหาก)

## กฎทางธุรกิจ / เงื่อนไข (Business Rules)
- เฉพาะบทบาทผู้บริหารร้าน (เจ้าของร้าน/ผู้จัดการร้าน) เท่านั้นที่มีสิทธิ์สร้าง/แก้ไข/ปลดบัญชีพนักงาน (รวมถึงบัญชีผู้บริหารร้านคนอื่น) — บทบาทอื่นไม่มีสิทธิ์นี้
- ข้อมูลบัญชีผู้ใช้ของพนักงานแต่ละคนต้องไม่ซ้ำกันในระบบ
- 1 บัญชีพนักงานมีได้ 1 บทบาทเท่านั้น จาก 3 บทบาท (พนักงานเสิร์ฟ/บาริสต้า/ผู้บริหารร้าน)
- PIN code ผูกกับบัญชีพนักงาน 1:1 เพื่อใช้ยืนยันตัวตนและระบุตัวผู้ทำรายการอย่างแม่นยำ
- การยืนยันตัวตนด้วย PIN ทำเป็นรายเครื่อง/อุปกรณ์ (device-based) ไม่ใช่การ login แบบ session ข้ามอุปกรณ์แบบมาตรฐาน
- กรณีลืม PIN ต้องให้ผู้บริหารร้านรีเซ็ตให้แบบ manual เท่านั้น ไม่มีช่องทาง self-service
- พนักงานที่ถูกปลดออกจากระบบ (offboarded) ต้อง login ไม่ได้อีกทันที
- การปลดพนักงานออกจากระบบเป็นจุดเริ่มต้น (trigger) ของการนับระยะเวลา retention/anonymization 90 วัน ที่กำหนดไว้ใน [[../../03-testing/01-test-plan/test-plan|test-plan.md]] หัวข้อ 5.4 และจะถูกระบุรายละเอียดกลไกเพิ่มเติมในการแก้ไข [[20260802-003-audit-log|20260802-003]]/[[20260802-004-pdpa-consent|20260802-004]]

## เอกสารที่เกี่ยวข้อง

- [[../02-plan/index|02-plan]] — แผนงานที่จะแตกออกจากเอกสารนี้
- [[20260802-001-table-qr-ordering|ระบบสั่งกาแฟจากโต๊ะด้วยการสแกน QR Code]] — ระบบหลักที่พนักงานต้องยืนยันตัวตนก่อนใช้งาน
- [[20260802-002-sales-dashboard|หน้า Dashboard ดูยอดขาย]] — ต้องอาศัย RBAC และการยืนยันตัวตนจากเอกสารนี้ในการจำกัดสิทธิ์เข้าถึง
- [[20260802-003-audit-log|ระบบบันทึก Log (Audit Trail)]] — ต้องอาศัย session/การยืนยันตัวตนจากเอกสารนี้ในการระบุผู้ทำรายการ และมี NFR retention/anonymization ที่ผูกกับ offboarding
- [[20260802-004-pdpa-consent|ขอความยินยอม (Consent) ตาม PDPA จากพนักงาน]] — consent gate ตอน onboarding อ้างอิงบัญชีพนักงานที่นิยามไว้ในเอกสารนี้ และมี NFR retention/anonymization ที่ผูกกับ offboarding เช่นกัน
- [[../../03-testing/01-test-plan/test-plan|test-plan.md]] — หัวข้อ 5.4 กำหนด NFR retention/anonymization 90 วัน ที่ trigger จากการ offboarding ในเอกสารนี้

## หมายเหตุ

- requirement นี้เป็น prerequisite ที่ต้องปิดก่อนจึงจะ implement [[20260802-002-sales-dashboard|20260802-002]], [[20260802-003-audit-log|20260802-003]] และ [[20260802-004-pdpa-consent|20260802-004]] ได้จริง เนื่องจากทั้ง 3 spec สมมติว่ามีบัญชี/บทบาท/การยืนยันตัวตนอยู่แล้วโดยไม่ได้ระบุรายละเอียด
- ผู้ใช้ยืนยันชัดเจนว่ากลไกยืนยันตัวตนเป็น PIN code ต่อเครื่อง/อุปกรณ์ ไม่ใช่ username+password มาตรฐาน และไม่มี self-service reset หรือ MFA ในเฟสนี้
- รายละเอียดกลไก anonymize ข้อมูลหลัง offboarding ครบ 90 วัน ตั้งใจไม่ระบุซ้ำในเอกสารนี้ เพราะจะถูกเพิ่มในการแก้ไข spec 20260802-003/20260802-004 เป็นงานถัดไป
- ผลการตรวจสอบเอกสารเดิม: grep คำว่า "บัญชี", "PIN", "ยืนยันตัวตน", "login", "เข้าสู่ระบบ", "บทบาท", "RBAC" (case-insensitive) ในโฟลเดอร์ `01-requirements/01-spec/` พบว่ามีการอ้างถึงบัญชีผู้ใช้/บทบาทในเอกสาร 20260802-001, 002, 003, 004 แต่ไม่มีฉบับใดระบุรายละเอียดการจัดการบัญชีพนักงานหรือกลไกยืนยันตัวตน จึงไม่พบเอกสารเดิมที่ทับซ้อน และสร้างเป็นเอกสารใหม่แยกต่างหากตามที่คาดไว้
